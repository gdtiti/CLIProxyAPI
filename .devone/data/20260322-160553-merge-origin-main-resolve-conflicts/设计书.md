## 方案摘要

- 推荐方案:
  先以当前 merge 索引为准识别真实未合并文件，再按测试、translator、watcher、conductor 几类逻辑逐块合并，最后只运行与改动直接相关的目标包验证。
- 推荐原因:
  该方案既能避免对无关区域做扩散性修改，也能把两边新增能力合并进同一实现，降低“冲突虽清零但行为回退”的风险。

## 备选方案对比

### 方案 A

- 做法:
  基于 `git diff --name-only --diff-filter=U` 锁定真实冲突文件；按每个文件的语义差异逐块合并，优先保留更完整、更新的实现，再做目标包测试。
- 收益:
  改动范围最小，冲突取舍可追溯，且验证范围与实际影响面一致。
- 代价:
  需要逐文件阅读和逐块判断，不能靠自动选择 `ours/theirs`。
- 风险:
  若判断失误，可能出现“代码能编译但丢了一侧新能力”的隐性回退。

### 方案 B

- 做法:
  对每个冲突文件直接偏向单侧版本，再补少量语法修复让测试通过。
- 收益:
  表面上更快。
- 代价:
  容易丢失另一侧新增能力，且后续排查回退成本高。
- 风险:
  会把“冲突已解决”误写成“功能仍完整”，形成假验收。

## 锁定设计

- 入口模块:
  6 个真实冲突文件及其直接测试/调用链。
- 关键调用链:
  `git diff --name-only --diff-filter=U` -> 文件级语义对比 -> 冲突块合并 -> 目标包 `go test`。
- 数据流:
  merge 索引中的冲突块输入到人工合并决策，再进入目标包验证与任务包回写。
- 错误处理:
  若目标包验证失败，先判断是否是本轮修改导致；若失败来自无关现存问题，则显式隔离记录，不混成本轮冲突失败。
- 配置变更:
  无。

## 分阶段计划

### 阶段 1

- 目标:
  锁定真实冲突文件并按领域分组。
- 风险主题:
  错把语法冲突当成纯文本冲突，漏掉语义差异。
- 主要变更:
  无业务实现新增；只在冲突文件内做合并取舍。
- 验证方式:
  `git diff --name-only --diff-filter=U`
- 完成标志:
  能明确列出每个需要处理的真实冲突文件。

### 阶段 2

- 目标:
  完成逐块合并并清空未合并索引。
- 风险主题:
  功能回退、兼容性破坏、错误偏向旧实现。
- 主要变更:
  修改 6 个冲突文件，合并双方逻辑。
- 验证方式:
  `git diff --name-only --diff-filter=U`
- 完成标志:
  未合并文件列表清零。

### 阶段 3

- 目标:
  证明直接受影响模块未因冲突解决而回退，并给出验收与收尾依据。
- 风险主题:
  把无关现存失败误判为本轮冲突失败，或在主工作区脏状态下误做高风险合并。
- 主要变更:
  无新增代码；执行目标包测试、acceptance/completion gate 与 worktree 对账。
- 验证方式:
  `go test ./internal/translator/codex/openai/chat-completions ./internal/translator/codex/openai/responses ./internal/translator/openai/openai/responses`
  `go test ./internal/watcher`
  `go test ./sdk/cliproxy/auth`
  `go test ./internal/runtime/executor`
- 完成标志:
  能明确区分“验收已通过”和“是否可直接 merge/cleanup”。

## 非目标

- 修复与本轮冲突无直接关系的整仓现存失败
- 未经确认直接把当前脏工作区合并回主线
- 为了快而使用单侧覆盖式冲突解决

## 设计评审结论

- 用户是否批准:
  是，用户明确要求“详细分析每个冲突，逐块解决冲突，尽可能保留两个版本的功能完整，更好的更新的功能优选”。
- 批准范围:
  仅针对当前真实 merge 冲突现场及其直接验证范围。
- 备注:
  在 `required-only` 下，不扩展到无关整仓修复、主线 merge 或目录清理。
