## 方案摘要

- 推荐方案:
  先做纯 git 证据核对，再执行正式 `fetch + merge`；只有真正出现冲突标记时，才进入逐文件兼容性分析和解决。
- 推荐原因:
  该方案能避免在“其实已包含上游提交”的情况下误做无意义冲突处理，并保留最强可验证性。

## 备选方案对比

### 方案 A

- 做法:
  执行 `git fetch origin`、`git rev-list --left-right --count origin/main...HEAD`、`git merge origin/main`，以真实输出决定是否进入冲突解决。
- 收益:
  证据最直接；不会伪造冲突；若已对齐上游可立即结束。
- 代价:
  需要先做一轮 git 现场核对，不能跳过。
- 风险:
  用户预期与现场不一致时，需要如实报告“无冲突”。

### 方案 B

- 做法:
  直接假设存在冲突并预先读取潜在热点文件。
- 收益:
  表面上更快。
- 代价:
  可能浪费上下文，并产生错误分析。
- 风险:
  若 `origin/main` 已被当前分支包含，会形成虚假的冲突处理结论。

## 锁定设计

- 入口模块:
  本地 git 元数据与 merge 命令。
- 关键调用链:
  `git fetch origin` -> 差异统计 -> `git merge origin/main` -> 如有冲突再进入逐文件分析。
- 数据流:
  远端引用更新到本地 -> 计算祖先关系 -> merge 输出决定后续路径。
- 错误处理:
  若 merge 报冲突，则按文件逐块解决；若 merge 直接返回 `Already up to date.`，则停止进入代码层处理。
- 配置变更:
  无。

## 分阶段计划

### 阶段 1

- 目标:
  核对当前分支与 `origin/main` 的真实差异关系。
- 风险主题:
  错把已包含上游的分支当成待合并分支。
- 主要变更:
  无代码变更，仅 git 现场核对。
- 验证方式:
  `git status --short --branch`
  `git remote show origin`
  `git rev-list --left-right --count origin/main...HEAD`
- 完成标志:
  能明确回答“是否真的有上游提交待合并”。

### 阶段 2

- 目标:
  执行真实 merge，并在必要时解决冲突。
- 风险主题:
  功能回退、兼容性破坏、误解 merge 结果。
- 主要变更:
  本轮实际执行了 `git merge origin/main`，但结果为无变更。
- 验证方式:
  merge 命令原始输出与 merge 后仓库状态。
- 完成标志:
  明确得到“冲突已解决”或“无冲突可解”的可追溯结论。
