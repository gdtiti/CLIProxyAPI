## 问题定义

- 当前问题: 管理端 `/usage` 与 `/monitor` 页面在 PostgreSQL 持久化场景下经常显示“无统计数据”，即使数据库已有聚合记录。
- 影响对象: 管理端运营人员、开发排障人员、统计报表消费方。
- 触发背景: 后端 `GetUsageStatistics` 在 PG 路径优先使用 `QuerySnapshot`，该结构仅返回聚合字段但未回填 `apis.models.details`；前端过滤和图表逻辑依赖 details，导致二次筛选后清空。
- 为什么现在处理: 已出现“页面完全看不到统计分析数据”的用户可见故障，影响日常运营判断。

## 目标与成功标准

- 目标 1: 后端 PG 路径返回的数据结构与内存路径保持契约一致，包含 `apis -> models -> details`（在查询窗口内）。
- 目标 2: 前端在 `details` 缺失时不再整体归零，能够退化显示聚合统计并保留可视化。

## 范围边界

### 本次必须完成

- 修复后端 PG 查询快照缺失 details 的问题。
- 修复 `range=all` 未生效、默认回落 24h 的问题。
- 为前端 `usage` 与 `monitor` 增加无 details 兼容回退。
- 补充后端单元测试，覆盖 PG 快照回填与时间范围解析。

### 本次明确不做

- 不改动统计埋点采集协议。
- 不做历史数据重灌或离线回填脚本。
- 不改动与统计无关的页面和 API。

## 验收真相陈述

- [REQ-001] 当使用 PG 存储时，`/v0/management/usage` 在 `7d` 与 `all` 范围下返回 `details`，且与聚合字段可对应。
- [REQ-002] 前端在 `details` 为空或缺失时，卡片与趋势图不再整体清空；仍能展示聚合结果并明确能力边界。

## 约束与依赖

- 技术约束: 不引入破坏性数据库迁移；保持现有 API 字段兼容。
- 业务约束: 线上页面不能继续“假空白”。
- 外部依赖: 需要 `usage-statistics-enabled: true` 才会有新采集数据。

## 风险与待确认项

- 风险: 大时间窗口下 details 体量可能上升，需控制查询与响应大小。
- 待确认: 历史仅有聚合、无明细的数据无法逆向恢复；通过前端回退保障可见性。
