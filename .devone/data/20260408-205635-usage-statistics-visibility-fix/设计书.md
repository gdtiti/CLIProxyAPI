## 方案摘要

- 推荐方案: 后端在 PG 快照查询时追加明细回填 + 时间范围修复；前端增加聚合回退渲染。
- 推荐原因: 既修复根因（后端契约缺失），也增强前端抗不完整数据能力，能同时覆盖新旧数据。

## 备选方案对比

### 方案 A

- 做法: `QuerySnapshot` 回填 `details`，`parseTimeRange` 支持 `all`，前端无 details 回退。
- 收益: 前后端双保险，页面可见性稳定。
- 代价: 需要后端+前端双侧改动与测试。
- 风险: 大窗口查询的明细量需控制。

### 方案 B

- 做法: 仅改前端，不改后端。
- 收益: 交付快。
- 代价: 根因未消除，接口契约继续漂移。
- 风险: 后续统计能力扩展仍会反复出问题。

## 锁定设计

- 入口模块:
  - 后端 `internal/api/handlers/management/usage.go`
  - 后端 `internal/usage/query.go`
  - 前端 `Cli-Proxy-API-Management-Center/src/utils/usage.ts`
  - 前端 `Cli-Proxy-API-Management-Center/src/pages/MonitorPage.tsx`
- 关键调用链:
  - `GetUsageStatistics -> parseTimeRange -> store.QuerySnapshot`
  - `UsagePage/MonitorPage -> filterUsageByTimeRange/collectUsageDetails`
- 数据流: PG `usage_aggregates` 提供聚合，`usage_details` 提供明细，API 统一输出。
- 错误处理: 明细缺失时不抛伪成功；前端显式走聚合回退。
- 配置变更: 无新增配置键，保留现有 `usage-statistics-enabled`。
