## 问题定义

- 当前问题:
  当前仓库已经具备 `PersistAuthFiles(ctx, message, paths...)` 底层能力，也已经有
  `POST /v0/management/auth-files/reload-from-store` 这类“store -> 本地 -> runtime”
  的管理接口，但没有一个明确的 management 端点把当前节点 `cfg.AuthDir` 下的
  auth 文件批量同步到当前 token store。
- 影响对象:
  使用 PostgreSQL / object store / git store 作为共享 auth store 的部署，以及需
  要在某个节点上手工补齐 auth 文件后再把结果持久化到共享 store 的运维场景。
- 触发背景:
  用户已确认“上传 auth file”链路的问题已经修复，但还需要一个显式接口，把当前
  节点 auth 目录中的现有文件一次性推送到 PG 持久化，而不是依赖逐个重传文件或
  watcher 异步发现。
- 为什么现在处理:
  目前运维动作缺少一个低歧义、可审计的入口。继续依赖“改文件碰碰 watcher”或
  “逐个重传”会放大人为操作成本，也不利于前端或管理端给出稳定操作流。

## 目标与成功标准

- 目标 1:
  新增一个 management 接口，将当前节点 `cfg.AuthDir` 下可识别的 auth `.json`
  文件批量同步到当前 token store，并对 PostgreSQL 等共享 store 形成可观察的
  持久化结果。
- 目标 2:
  接口成功语义要清晰，返回至少包含枚举总数与实际提交数量；当当前 store 不支持
  `PersistAuthFiles` 或持久化失败时，请求必须返回非 200，并暴露明确错误。

## 范围边界

### 本次必须完成

- 新增一个管理路由，语义锁定为“当前节点 `authDir` 文件 -> 当前 store”，不混入
  其它节点 reload。
- 在 handler 中枚举 `cfg.AuthDir` 下的 auth `.json` 文件，并复用现有
  `PersistAuthFiles` 抽象批量持久化。
- 补充定向测试，覆盖成功持久化、store 不支持、以及 store 返回错误三条主路径。
- 将新接口的范围边界、设计取舍与测试计划写回 DevOne 文档包。

### 本次明确不做

- 不把接口语义扩展成“authManager 当前内存态 -> store”的反序列化能力。
- 不新增跨节点自动广播、自动轮询或自动执行 `reload-from-store` 的机制。
- 不顺手改造 watcher、auth file JSON 结构或前端页面交互。

## 验收真相陈述

- [REQ-001] 调用新接口成功后，handler 会将 `cfg.AuthDir` 下纳入范围的 auth
  `.json` 文件批量交给当前 store 的 `PersistAuthFiles`，并返回 `target=auth-files`
  与本次同步计数。
- [REQ-002] 当当前 store 不支持 auth 文件持久化，或 `PersistAuthFiles` 返回错误
  时，接口返回非 200，且不会谎称同步成功。

## 约束与依赖

- 技术约束:
  继续复用现有 `tokenStoreWithBaseDir()` 与 `authFilesStorePersister` 抽象，不新造
  PG 专用旁路；文件来源限定为当前节点 `cfg.AuthDir` 落盘后的 `.json`。
- 业务约束:
  用户当前要求的是“补充一个明确的批量持久化接口”，而不是扩展成多节点自动生效
  框架或 runtime 内存态导出工具。
- 外部依赖:
  PostgreSQL / object / git store 侧都已有 `PersistAuthFiles` 能力；管理接口只负
  责把文件推入 store，不负责让其它节点自动读取新值。

## 风险与待确认项

- 风险:
  如果运维误以为该接口会让其它节点立刻看到新 auth，仍会出现“PG 已更新但其它节
  点未 reload”的认知偏差，因此接口描述与返回字段必须强调这是 push-to-store，
  不是 cluster-wide reload。
- 待确认:
  当前推荐先做“无请求体、全量同步当前 authDir”的最小接口。若后续需要只同步部
  分文件或增加 dry-run，应另开范围，而不是把首版接口做成复杂可选语义合集。
