## 方案摘要

- 推荐方案:
  新增 `POST /v0/management/auth-files/persist-to-store`，在 handler 中枚举当前
  `cfg.AuthDir` 下的 `.json` 文件，调用 `tokenStoreWithBaseDir()` 获取当前
  store，并通过 `PersistAuthFiles(ctx, message, paths...)` 一次性推送到 store。
- 推荐原因:
  这条路径复用现有抽象，不需要引入“runtime 内存态反序列化”新复杂度，也避免把
  “推到共享 store”和“其它节点立即 reload”混成一个高耦合接口。

## 备选方案对比

### 方案 A

- 做法:
  不新增接口，继续依赖 watcher 在本地文件变更后异步调用 `PersistAuthFiles`。
- 收益:
  改动最小，无需新增路由和测试。
- 代价:
  运维动作不显式，必须通过“改文件”间接触发；无法稳定告诉调用方哪些文件已被同
  步到 store。
- 风险:
  watcher 的时序和可用性重新变成接口契约外的隐含前提，排障成本高。

### 方案 B

- 做法:
  新增 `POST /v0/management/auth-files/persist-to-store`，只做当前节点
  `authDir -> store` 的显式批量同步，返回总数与同步结果。
- 收益:
  契约清晰、实现复用度高、测试边界明确；同时规避“persist 成功后还要再做
  runtime reload”的额外原子性问题。
- 代价:
  需要补一个新的 handler、路由和测试桩。
- 风险:
  调用方若把它当成“全节点即时生效”接口，仍会误用；需要在命名和返回字段上明确
  边界。

### 方案 C

- 做法:
  直接新增一个“推送到 store 并通知其它节点 reload”的复合接口。
- 收益:
  表面上更接近“调用一次全都生效”的想象。
- 代价:
  需要引入跨节点协调、失败补偿和一致性协议，远超当前需求。
- 风险:
  需求范围膨胀，难以在当前波次给出可信验证。

## 锁定设计

- 入口模块:
  `internal/api/handlers/management/auth_files.go`
  `internal/api/server.go`
  `internal/api/handlers/management/*_test.go`
- 关键调用链:
  `PostPersistAuthFilesToStore -> listPersistableAuthFiles -> tokenStoreWithBaseDir ->
  PersistAuthFiles`
- 数据流:
  handler 从 `cfg.AuthDir` 枚举 `.json` 文件，构造稳定路径列表，校验当前 store
  是否实现 `authFilesStorePersister`，然后一次性调用 `PersistAuthFiles`。返回体
  只描述“推送到 store”的结果，不触碰 runtime reload hook。
- 错误处理:
  若 handler 未初始化、`cfg.AuthDir` 未配置、store 不支持持久化、枚举目录失败
  或 `PersistAuthFiles` 失败，统一返回非 200；只有 store 真正接受持久化请求后
  才返回成功。
- 配置变更:
  无新增配置项，继续复用现有 `cfg.AuthDir` 和 token store。
