## 方案摘要

- 推荐方案: 参考现有 `.github/workflows/docker-branch.yml` 的 GHCR 写法，把 `docker-image.yml` 重构为单 job 的 multi-arch GHCR 发布流程。
- 推荐原因: 这是仓库内已存在、已验证的 GHCR 模式；可以同时去掉 DockerHub 登录、临时架构标签和 DockerHub tag cleanup，减少失败点与维护成本。

## 备选方案对比

### 方案 A

- 做法: 使用 `REGISTRY=ghcr.io` + `IMAGE_NAME=${{ github.repository }}`，在单个 job 中配置 `packages: write`、GHCR 登录、`docker/metadata-action` 自动生成 `latest` / `${VERSION}` 标签，并用一次 `build-push-action` 完成 `linux/amd64` + `linux/arm64` 多架构发布。
- 收益: 最小化 secrets 依赖；直接复用现有 GHCR 模式；避免三 job + imagetools + cleanup 的额外复杂度。
- 代价: 发布实现方式从“两次单架构构建 + manifest 合成”变成“单次 multi-arch 构建推送”，workflow 结构会明显变化。
- 风险: 若 runner 对 QEMU / multi-arch 构建支持异常，可能需要回退到双 job 方案。

### 方案 B

- 做法: 保留原三 job 结构，仅把 DockerHub 登录与 tag 目标替换成 GHCR，并用 GHCR manifest 替代 DockerHub cleanup。
- 收益: 变更面较窄，保留当前 job 拆分。
- 代价: 仍要维护三处重复登录、三处元数据生成和 manifest 拼装逻辑。
- 风险: 重复步骤更多，后续再维护时仍容易出现配置漂移。

## 锁定设计

- 入口模块: `.github/workflows/docker-image.yml`
- 关键调用链: `workflow_dispatch/tag push -> checkout -> refresh models catalog -> setup qemu/buildx -> login ghcr -> generate metadata -> docker metadata -> build-push multi-arch`
- 数据流: `github.ref_name` 生成 `VERSION`，再由 `metadata-action` 生成 `ghcr.io/${{ github.repository }}:{latest,VERSION}` 标签供 build-push 使用。
- 错误处理: 不新增静默降级；如 GHCR 登录或 build-push 失败，workflow 直接失败并暴露在 job 日志中。
- 配置变更: 新增 `REGISTRY` / `IMAGE_NAME` env；新增 `permissions.packages: write`；删除 DockerHub 相关 env 与 cleanup。
