## 问题定义

- 当前问题:
  - 当前项目已经支持按累计请求次数删除文件型 `codex` auth，也支持在 `usage_limit_reached` 或配置状态码命中时禁用 auth，但还不支持“每累计 N 次请求主动做一次 Codex quota/usage 探测，并在探测返回 `401` 时立即删除账号”。
- 影响对象:
  - `auth-maintenance` 配置层。
  - management 侧 `AuthRuntimeMaintenanceHook` 的请求结果处理链路。
  - 文件型 `codex` auth 的运行态累计请求计数与删除行为。
- 触发背景:
  - 用户要求在现有请求次数删除能力之外，再增加一个开关，用于控制“每多少次请求检查一次 quota”，并在 quota 检查提示 `401` 时直接删除该账号。
- 为什么现在处理:
  - 当前相关逻辑已经集中在 management runtime hook 和运行态持久化里，继续沿这一条链路扩展的改动面最小，也最容易避免和既有 `401` 阈值删除、`usage_limit_reached` 禁用逻辑相互污染。

## 目标与成功标准

- 目标 1:
  - 新增可配置项，允许为文件型 `codex` auth 设置“每 N 次请求做一次 quota 检查”的间隔，`0` 表示关闭。
- 目标 2:
  - 命中检查间隔时，主动请求 Codex usage API；若响应状态为 `401`，复用现有删除链路删除 auth 文件并禁用运行态账号。

## 范围边界

### 本次必须完成

- 配置结构新增 quota 检查间隔字段，默认 `0` 关闭，并补齐配置解析测试。
- 在 management runtime hook 中复用现有累计请求计数，只在命中间隔时发起 Codex usage 探测。
- 当 usage 探测返回 `401` 时，复用现有 `removeManagedAuthFile` 删除账号。
- 补齐最小单元测试，覆盖开启、关闭、`401` 删除和非 `401` 不删除。

### 本次明确不做

- 不新增第二套后台维护线程或扫描器。
- 不修改非 `codex` provider 的行为。
- 不改变现有 `codex-max-request-count` 删除语义和 `usage_limit_reached` 禁用语义。
- 不把 quota 探测结果扩展成新的 cooldown、disable 或 backoff 语义；本轮只消费 `401` 删除。

## 验收真相陈述

- [REQ-001] 配置文件支持声明 `auth-maintenance.codex-quota-check-request-interval`，未配置或配置为 `0` 时保持旧行为。
- [REQ-002] 文件型 `codex` auth 在累计请求数命中配置间隔时会主动请求 usage API，若该请求返回 `401`，认证文件会被删除且运行态 auth 被标记为禁用。

## 约束与依赖

- 技术约束:
  - 必须复用现有 management runtime hook、累计请求计数和 `removeManagedAuthFile` 删除链路，不引入隐藏回退。
- 业务约束:
  - “请求次数”延续既有实现，按所有已完成请求累计，不区分成功或失败。
  - 只对文件型 `codex` auth 生效。
- 外部依赖:
  - 依赖现有 auth manager、config 加载、Codex usage API 请求头格式，以及 management handler 的真实文件删除路径。

## 风险与待确认项

- 风险:
  - 若重复累计次数逻辑实现不当，可能导致同一次请求被双计数，进而提前触发删除或 quota 检查。
  - 若 quota probe 不能正确复用 access token / account id / base URL，可能会出现误判或无效探测。
- 待确认:
  - 本轮按“达到配置间隔时只认 usage API 返回 `401` 才删除”实现，其他状态码仅保留原有行为；这符合用户最新要求。
