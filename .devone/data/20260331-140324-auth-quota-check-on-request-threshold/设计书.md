## 方案摘要

- 推荐方案:
  - 在 `auth-maintenance` 下新增 `codex-quota-check-request-interval` 配置；把 management runtime hook 里现有的 Codex 请求计数删除逻辑收敛成一个统一的“请求计数维护”入口，在同一次计数结果上同时处理 `codex-max-request-count` 和 quota probe。
- 推荐原因:
  - 现有 `RecordCompletedRequest`、`removeManagedAuthFile`、文件型 auth 判定都已经在 management hook 一侧闭环；复用这条链路可以避免双计数、避免新增第二套维护状态，也不需要把 executor 的完整配额解析逻辑搬到 management 层。

## 备选方案对比

### 方案 A

- 做法:
  - 每次 `codex` 文件 auth 请求完成后只累计一次请求数；先判断 `codex-max-request-count` 是否达到上限，再在命中 `codex-quota-check-request-interval` 时发起 usage API 探测，若返回 `401` 则删除 auth。
- 收益:
  - 最小改动即可满足需求；累计请求数仍可跨重启保留；两种“按请求数触发”的能力共享同一计数。
- 代价:
  - 需要同时修改配置、management hook、少量 service 配置归一化判断与测试。
- 风险:
  - 需要小心处理“阈值删除”和“间隔探测”的优先级，避免重复写盘或双删除。

### 方案 B

- 做法:
  - 另起一套 quota probe 计数器或后台探测逻辑，不复用现有 `RecordCompletedRequest`。
- 收益:
  - 可以把 quota 探测与请求总次数删除完全分离。
- 代价:
  - 需要维护第二套计数与状态，容易和当前运行态持久化、reload、删除链路产生不一致。
- 风险:
  - 双计数和状态漂移风险高，因此不采用。

## 锁定设计

- 入口模块:
  - `internal/config/config.go`
  - `internal/api/handlers/management/auth_files_runtime_hook.go`
  - `sdk/cliproxy/service_auth_maintenance.go`
- 关键调用链:
  - `sdk/cliproxy/auth/Manager.MarkResult -> authRuntimeMaintenanceHook.OnResult -> codex 请求计数维护 -> removeManagedAuthFile`
  - 命中 quota 检查间隔时：`authRuntimeMaintenanceHook.OnResult -> managedCodexUsageProbe -> executor.NewCodexExecutor(...).HttpRequest`
- 数据流:
  - 配置从 `auth-maintenance.codex-quota-check-request-interval` 进入 `AuthMaintenanceConfig`。
  - 运行态累计请求数继续持久化在 `auth.Metadata[cliproxy_runtime_state]`。
  - usage probe 复用 auth 的 `access_token`、`account_id` 和可选 `base_url`。
- 错误处理:
  - usage probe 返回 `401` 时走现有删除链路。
  - usage probe 失败或返回非 `401` 时不删除，只保留累计计数并显式 warning。
  - 删除失败时沿用现有逻辑，把最新计数回写到 auth manager。
- 配置变更:
  - 新增 `auth-maintenance.codex-quota-check-request-interval`
  - `0` 表示关闭；`>0` 表示每累计 N 次请求后做一次 quota probe。
