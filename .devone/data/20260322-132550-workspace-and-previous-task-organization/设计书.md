## 方案摘要

- 推荐方案:
  采用“文档归档优先”的整理方案：新建一个独立 DevOne 任务包，只做事实盘点、归属判定、继续入口收束，不触碰业务代码与危险清理。
- 推荐原因:
  这是风险最低、最可追溯的整理方式，既能把历史任务状态收口，又不会把当前脏工作区进一步污染。

## 备选方案对比
### 方案 A

- 做法:
  读取历史任务包、主工作区和 worktree 状态，形成新的恢复任务包。
- 收益:
  安全、可验证、可恢复，不影响现有未提交改动。
- 代价:
  只能完成“整理与收口”，不能替代真正的删除或合并。
- 风险:
  后续如果用户想继续物理清理，仍需一次明确确认。

### 方案 B

- 做法:
  直接删除旧 worktree、清理临时目录、合并分支，并把主工作区改动整理到单一路径。
- 收益:
  工作区会更干净，历史残留更少。
- 代价:
  涉及删除和合并，属于高风险不可逆操作。
- 风险:
  若任务归属判断有误，会直接损伤当前未提交成果。

## 锁定设计

- 入口模块:
  `.devone/data/`、`.devone/worktree/`、主工作区 git 状态、各历史任务包文档。
- 关键调用链:
  用户请求
  -> 读取 `devone` / `devone-workflow` 规则
  -> 盘点 `.devone/data` 与 `git worktree list`
  -> 检查主工作区与各 worktree 状态
  -> 创建新的整理任务包
  -> 回写整理结论与恢复入口。
- 数据流:
  历史任务包和 git 现场
  -> 整理结论
  -> 当前任务包六份文档
  -> 后续继续执行入口。
- 错误处理:
  对删除、合并、worktree 移除等动作一律不自动执行，只在文档中标记为待确认。
- 配置变更:
  无。

## 分阶段计划
### 阶段 1

- 目标:
  收集事实并锁定继续入口。
- 风险主题:
  把主工作区的改动误归类到错误任务包。
- 主要变更:
  读取历史任务包、盘点 worktree、比对主工作区与活跃 worktree 的脏文件集合。
- 验证方式:
  通过 `git status`、`git worktree list`、`git -C <worktree> status`、任务包文档内容交叉验证。
- 完成标志:
  能明确指出“哪个任务应继续、哪个任务只需归档、哪些清理不能自动做”。

### 阶段 2

- 目标:
  把整理结论回写到当前任务包并形成恢复手册。
- 风险主题:
  文档结论与现场状态不一致。
- 主要变更:
  更新当前任务包的需求、设计、知识、测试和技术说明。
- 验证方式:
  重新检查 git 状态，确认没有新增业务代码改动，只新增当前任务包文档。
- 完成标志:
  新任务包可直接作为后续恢复入口使用。

## 非目标
- 本轮不初始化 `.devone/wiki/`。
- 本轮不重跑历史任务的完整测试集。
- 本轮不做业务代码实现、分支合并或 worktree 删除。

## 设计评审结论

- 用户是否批准:
  是。用户明确要求“为我整理工作区和之前的任务”，并指定 `devone`。
- 批准范围:
  文档化整理、状态归档、继续入口收束。
- 备注:
  执行模式采用代理假设 `required-only`，且不包含任何危险操作。
