## 方案摘要

- 推荐方案:
  - 在 `internal/watcher` 内部增加周期性自动重载 ticker，并在认证文件缓存构建链路中引入分批并发处理与缓存复用。
- 推荐原因:
  - watcher 已是配置监听、手动重载、auth update queue 的汇聚点，在该层统一管理自动轮询生命周期最稳定。
  - 在现有 watcher 主链增强，能保留当前仓库已有的 runtime hook、持久化与分布式同步能力，避免因套用参考仓库而产生回退。

## 备选方案对比

### 方案 A

- 做法:
  - 在 watcher 内部起周期性 ticker，tick 时先判断 config hash，再决定走 config reload 还是 auth refresh；认证文件全量重建改为分批并发并一次性提交缓存。
- 收益:
  - 生命周期集中，调用链清晰。
  - 容易复用现有 watcher 锁、队列与状态缓存。
  - 便于避免 config reload 和 auth refresh 的重复扫描。
- 代价:
  - 需要调整 `reloadClients`、`refreshAuthState` 和 cache 结构之间的契约。
- 风险:
  - 若缓存边界定义不清，可能造成 config 变更后 auth synth 结果未同步。

### 方案 B

- 做法:
  - 在 `sdk/cliproxy/service.go` 或外部调用方新增 ticker，定时调用现有手动 reload 入口。
- 收益:
  - 代码改动位置较少。
- 代价:
  - 自动重载生命周期分散到 watcher 外部，难以精准区分“配置变更”和“仅 auth 刷新”。
  - 更容易触发重复全量 reload，也更难与 watcher 内部状态去重逻辑对齐。
- 风险:
  - service 层和 watcher 层分散管理，后续维护成本更高。

## 锁定设计

- 入口模块:
  - `internal/config/config.go`
  - `internal/watcher/watcher.go`
  - `internal/watcher/events.go`
  - `internal/watcher/clients.go`
  - `internal/watcher/dispatcher.go`
- 关键调用链:
  - 配置加载时通过 `applyEnvironmentOverrides` 解析 `CLIPROXY_AUTO_RELOAD_INTERVAL_SECONDS`
  - watcher `start` 时根据配置启动自动重载 ticker
  - ticker tick 时先检测配置文件是否变化
  - 若配置变化，走现有 config reload 路径
  - 若配置未变化，仅走 auth refresh 路径
  - `reloadClients` 在需要刷新 auth 时统一重建文件缓存
  - `refreshAuthState` 优先复用 `fileAuthsByPath` 及相关 cache，而不是再次全量 synth 文件
- 数据流:
  - 环境变量 -> config override -> watcher runtime option
  - authDir 文件枚举 -> 分批并发读取/解析/合成 -> 聚合为新的 file cache -> 原子替换 watcher 内缓存 -> refresh auth state 复用 cache 生成最终授权视图
- 错误处理:
  - 自动重载执行失败时必须输出明确错误日志，不允许静默忽略。
  - 单个批次失败应中止本轮提交，避免提交部分成功、部分失败的认证状态。
- 配置变更:
  - 新增 `CLIPROXY_AUTO_RELOAD_INTERVAL_SECONDS`
  - 语义约定:
    - 空值或 `<= 0`: 关闭自动重载
    - `> 0`: 每 N 秒触发一次自动重载
