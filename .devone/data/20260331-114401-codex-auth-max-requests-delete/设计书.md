## 方案摘要

- 推荐方案:
  - 在 `auth-maintenance` 下新增 `codex-max-request-count` 配置；在 management runtime hook 的 `OnResult` 中对 `codex` 文件 auth 记录累计请求数，达到阈值后直接复用 `removeManagedAuthFile` 删除。
- 推荐原因:
  - 现有删除/禁用、reload、store 同步都已经在 management hook 内闭环，改动面最小且风险可控。

## 备选方案对比

### 方案 A

- 做法:
  - 扩展 `sdk/cliproxy/auth/runtime_persistence.go` 的持久化运行态结构，新增累计请求计数；hook 在每次 `codex` 请求结果后递增并判断阈值。
- 收益:
  - 计数可跨重启保留；实现复用现有 Metadata 持久化路径。
- 代价:
  - 需要同时修改配置、hook、运行态持久化与测试。
- 风险:
  - 若将来 auth 文件被外部重载，运行态 Metadata 合并策略仍需继续沿用现有行为。

### 方案 B

- 做法:
  - 把累计请求数直接写回 auth 文件。
- 收益:
  - 数据可直接随文件存在。
- 代价:
  - 会污染 auth 文件格式，并触发 watcher 重载与频繁磁盘写入。
- 风险:
  - 容易与现有文件语义、同步链路和外部工具兼容性冲突，因此不采用。

## 锁定设计

- 入口模块:
  - `internal/api/handlers/management/auth_files_runtime_hook.go`
- 关键调用链:
  - `sdk/cliproxy/auth/Manager.MarkResult -> hook.OnResult -> codex 请求计数 -> removeManagedAuthFile`
- 数据流:
  - 配置读取 `internal/config/config.go`
  - 运行态累计计数持久化到 `auth.Metadata[cliproxy_runtime_state]`
  - 达阈值后删除 auth 文件并禁用 auth 记录
- 错误处理:
  - 计数递增失败不应中断当前请求；删除失败按现有 hook 行为记录 warning 并保留 auth。
- 配置变更:
  - `auth-maintenance.codex-max-request-count`
  - `0` 表示关闭；`>0` 表示启用累计次数删除。
