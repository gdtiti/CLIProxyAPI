## 已知事实

- 现有实现:
  1. PostgreSQL store 在启动时会把 config 与 auth 从数据库同步到本地 spool
     目录。
  2. auth 上传链路会先把文件写到本地，再同步 PersistAuthFiles 到 store，
     成功后刷新当前节点运行态。
  3. config 修改主要走“写本地 config 文件 -> watcher reload -> 异步
     PersistConfig”链路。
  4. management API 已提供 `config.yaml/reload-from-store` 和
     `auth-files/reload-from-store` 手动回灌入口。
  5. usage 已有 PostgreSQL 持久化、小时聚合、按时间范围查询与
     `instance_id` 维度。

## 术语与定义

- 真相源:
  业务对象的权威持久化位置，本方案指 PostgreSQL。
- spool:
  节点本地镜像目录，供现有 file-based watcher 和 runtime 加载逻辑使用。
- outbox:
  与业务数据同事务提交的事件表，用来保证“数据提交”与“事件发布”一致。
- 增量同步:
  节点按对象版本只拉取变更部分，而不是每次全量 reload。
- 全量回灌:
  当节点检测到事件缺口、版本异常或 apply 失败时，从 PG 真相源重新镜像到
  本地。

## 调研结论

- 结论 1:
  现有架构适合作为分布式部署底座，因为它已经具备 shared PG store、
  startup bootstrap、runtime reload hook、usage PG aggregate 这些关键骨
  架。
- 结论 2:
  用户提出的“数据库更新后写 Redis 版本号和操作日志，再让低版本节点增量
  修改”方向是对的，但必须升级为“事务内 version/outbox + Redis 发布 +
  gap fallback”的完整协议，不能只做裸 Redis key。
- 结论 3:
  统计窗口不应以 Redis 原始计数为唯一真相；更稳妥的做法是继续以 PG 小时
  聚合为真相，Redis 只缓存 3h/6h/24h/日/月等物化结果。

## 风险假设

- 假设:
  1. 节点可以拿到稳定的 `node_id`，并允许按对象维护本地已应用版本。
  2. 可以接受“秒级最终一致 + 失败回退全量同步”，而不是强同步阻塞所有节
     点。
  3. PostgreSQL 可以新增版本/outbox 表，Redis 可以使用 Stream 或等价消费
     组模型。
- 验证方式:
  通过 2~3 节点集成测试验证并发写、节点重启、Redis 暂时不可用、事件丢失
  补偿。
