## 问题定义

- 当前问题:
  需要在现有 CLIProxyAPI Plus 架构上，先补齐“多节点共享 PostgreSQL +
  Redis”下的配置/凭证同步基础设施，并为后续统计窗口缓存留出明确实施路径。
- 影响对象:
  使用共享 PostgreSQL / Redis 的所有服务节点、管理端配置修改链路、auth
  file 上传链路，以及后续 usage 统计查询链路。
- 触发背景:
  用户希望多个节点连接同一套数据库和 Redis；一个节点更新数据库后，其他
  节点能够基于版本号和操作日志做增量同步；同时希望后续支持月、日、24h、
  6h、3h 等统计窗口。
- 为什么现在处理:
  代码里已经具备 PostgreSQL store、reload-from-store、runtime reload
  hook 等基础能力；最小可行路径是先把 config/auth 的分布式一致性收紧，再
  进入统计缓存阶段。

## 目标与成功标准

- 目标 1:
  基于现有 PostgresStore 和 runtime reload 能力，完成 Phase 1 的最小闭环。
- 目标 2:
  保证单个节点写入 config/auth 后，其他节点可通过 Redis 事件或 PostgreSQL
  版本轮询补偿收敛到一致状态。
- 目标 3:
  把统计窗口（月、日、24h、6h、3h）的后续数据分层、缓存策略和实施顺序写
  清楚，但不把它混进当前必备实现波次。

## 范围边界

### 本次必须完成

- 新增 `distributed-sync` 配置结构与样例配置。
- 在 PostgreSQL store 内引入 `sync_versions` / `sync_outbox`，让
  config/auth 写操作只在真实内容变化时 bump version/outbox。
- 使用 Redis Pub/Sub 广播变更事件，节点侧订阅后执行资源级
  `reload-from-store + runtime reload`。
- 增加 PostgreSQL version 轮询补偿，处理漏事件、重复事件、自发事件。
- 补充单元测试并完成目标包测试、服务编译，以及 DevOne 文档回写。

### 本次明确不做

- 不实现细粒度 patch 协议或复杂冲突合并。
- 不实现统计窗口缓存刷新、Redis materialized view 或使用面板改造。
- 不做真实多节点环境联调、生产发布或运维脚本收敛。

## 验收真相陈述

- [REQ-001] config/auth 写入与 version/outbox 记录具有同事务语义，且无实际
  内容变化时不会错误 bump 版本。
- [REQ-002] 其他节点在收到更高版本事件，或在 Redis 事件丢失时通过
  PostgreSQL 轮询补偿，都能触发配置/凭证回灌。
- [REQ-003] 自发事件、重复事件、旧版本事件不会触发重复 reload。
- [REQ-004] 统计窗口能力的后续实现顺序、数据分层和风险边界有明确文档。
