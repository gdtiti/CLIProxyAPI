## 方案摘要

- 推荐方案:
  Phase 1 采用“PostgreSQL 作为真相源 + `sync_versions` /
  `sync_outbox` 记录提交版本 + Redis Pub/Sub 做变更广播 +
  PostgreSQL 版本轮询做漏事件补偿”的最小闭环。
- 推荐原因:
  这条路线与现有代码最贴合：启动已具备 bootstrap/reload-from-store，运行态
  已具备 config/auth reload hook，因此无需先发明细粒度 patch 协议，也不需
  要把 Redis 提升为权威存储。

## 备选方案对比

### 方案 A

- 做法:
  不引入 Redis，只让各节点定时轮询 PostgreSQL 的 config/auth 版本并触发
  reload-from-store。
- 收益:
  简单，改动最少，验证路径直接。
- 代价:
  传播延迟较高，数据库轮询压力更大，也无法表达“刚发生了哪个对象变化”。
- 风险:
  管理端变更与节点可见之间的时间窗口不可控。

### 方案 B

- 做法:
  数据库写入成功后在同一事务内更新 `sync_versions` 和 `sync_outbox`，提交后
  再发布 Redis Pub/Sub 事件；节点消费事件并按资源做回灌，发现漏事件时回到
  PostgreSQL 版本轮询补偿。
- 收益:
  传播及时，同时保留 PostgreSQL 真相源与兜底补偿能力，适合先做 config/auth
  再扩展后续统计缓存。
- 代价:
  需要新增 schema helper、事件发布/消费组件，以及服务生命周期接线。
- 风险:
  如果写路径不做内容比较，会因为 watcher 回灌产生版本风暴。

## 锁定设计

- 入口模块:
  `internal/config/config.go`
  `config.example.yaml`
  `internal/store/postgresstore.go`
  `internal/store/distributed_sync.go`
  `internal/distributedsync/notifier.go`
  `internal/distributedsync/manager.go`
  `sdk/cliproxy/service.go`
- 关键调用链:
  `PersistConfig / PersistAuthFiles -> recordDistributedChangeTx ->
  publishDistributedChange`
  `Service.Run -> setupDistributedSyncNotifier -> startDistributedSync ->
  Manager.Start`
  `Manager.handleChange -> ReloadConfigFromStore + ReloadConfigFromDisk`
  `Manager.handleChange -> ReloadAuthFilesFromStore + ReloadAuthFiles(true)`
- 数据流:
  1. 节点写 config/auth 时，先写 PostgreSQL 真相表，再在同一事务内更新
     `sync_versions` 与 `sync_outbox`。
  2. 事务提交后异步发布 Redis Pub/Sub 事件，事件只携带资源、版本、操作和
     最小 payload。
  3. 其他节点收到事件后，忽略自发事件、旧版本事件和重复事件。
  4. 对更高版本事件执行资源级 reload-from-store，并刷新本地 runtime。
  5. 即使 Redis 漏事件，节点仍通过定时读取 PostgreSQL 版本表进行补偿。
- 错误处理:
  `PersistConfig` / `PersistAuthFiles` 先比较内容，只有真实变化才 bump
  version/outbox；Redis 发布失败不会回滚已提交的 PostgreSQL 写入，而是依赖
  后续轮询补偿；节点 apply 失败时记录错误并等待下一轮 reconcile 重试。
- 配置变更:
  新增 `distributed-sync.enabled`
  `distributed-sync.node-id`
  `distributed-sync.channel`
  `distributed-sync.poll-interval-seconds`
  `distributed-sync.redis.*`

## 分阶段计划

### 阶段 1

- 目标:
  落地 config/auth 的分布式同步最小闭环。
- 风险主题:
  既要避免事件丢失，又要避免 watcher 回灌后再次写回 store 形成事件风暴。
- 主要变更:
  新增 distributed sync 配置、schema helper、Redis notifier、manager、
  服务接线和第一批单元测试。
- 验证方式:
  `internal/store` 与 `internal/distributedsync` 单元测试；
  `sdk/cliproxy` 包测试；
  `go build ./cmd/server`。
- 完成标志:
  单节点写入后，其它节点可以通过 Redis 事件或 PostgreSQL 轮询补偿收敛到最
  新版本；重复/自发事件不会重复 apply。

### 阶段 2

- 目标:
  引入统计窗口缓存和管理面查询优化。
- 风险主题:
  统计窗口既要快，又不能与 PostgreSQL 真相产生长期漂移。
- 主要变更:
  基于 PG 小时聚合生成 3h / 6h / 24h / 日 / 月窗口缓存，提供失效、重建和查
  询接口收敛。
- 验证方式:
  用固定样本校验窗口边界，覆盖跨日、跨月、UTC 边界场景；补 Redis miss /
  rebuild / repeated invalidate 验证。
- 完成标志:
  管理端可稳定返回多个统计窗口，且 Redis 故障只影响时延，不影响正确性。

## 非目标

- 不把 Redis 作为配置/凭证的权威存储。
- 不在第一期解决复杂多主冲突合并，也不实现细粒度 patch 回放。
- 不取消现有本地 spool + watcher 机制；它仍是 runtime 装载层和全量回灌兜
  底层。
