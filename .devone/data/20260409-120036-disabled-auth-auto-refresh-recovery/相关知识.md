## 已知事实

- 现有实现:
  - `sdk/cliproxy/service.go` 启动时会同时启动 `startAuthMaintenance(ctx)` 和 `coreManager.StartAutoRefresh(..., 15*time.Minute)`。
  - 当前主工作区的 `sdk/cliproxy/service_auth_maintenance.go` 只有 disable/delete 维护动作，没有 disabled recovery 动作。
  - `sdk/cliproxy/auth/conductor.go` 的 `Manager.shouldRefresh()` 开头直接跳过 `a.Disabled`，因此 disabled auth 不会进入现有 auto-refresh。
  - `internal/api/handlers/management/auth_files_runtime_hook.go` 的 `handleCodexRequestMaintenance()` 只在请求结果回调时累积 request count / quota probe，目标必须是当前正在用的活跃 auth。
  - `internal/runtime/executor/codex_executor.go` 已有 `Refresh(ctx, auth)` 和 `/backend-api/wham/usage` probe helper，可直接复用。
  - `sdk/auth/filestore.go` 读写 auth 文件时以 `metadata + disabled` 为主，不会自动持久化 `StatusMessage`；仅靠运行态 status message 不能跨重启区分手动禁用和系统禁用。
  - `internal/usage/*` 只为 usage 统计提供 PG 持久化，当前没有通用业务事件表；仓库也没有 SQLite 依赖。
  - `internal/logging/global_logger.go` 与 `internal/api/handlers/management/logs.go` 提供通用文本日志目录与读取能力，但不是结构化恢复事件存储。

## 术语与定义

- 系统恢复标记:
  - 指 auth 文件 metadata 中能证明“该 disabled 状态来自系统自动维护，而不是人工手动禁用”的字段。
- disabled recovery:
  - 对 `disabled=true` 的文件型 `codex` auth 做 scan / refresh / probe / unlock 的后台维护链路。
- recovery event:
  - 一次 scan、skip、refresh、probe、unlock、failure 的结构化记录。

## 调研结论

- 结论 1:
  - disabled recovery 应挂到 `auth-maintenance`，不应硬塞进 `core auth auto-refresh`。原因是 auto-refresh 设计上面向活跃 auth，而 maintenance 已有路径聚合和文件写回能力。
- 结论 2:
  - 当前项目没有现成的结构化恢复日志存储；最小可靠方案是“服务内 recent memory buffer + append-only JSONL 持久化文件”。
- 结论 3:
  - 如果不补系统恢复标记，重启后无法安全地区分“management 手动禁用”和“runtime/maintenance 自动禁用”，容易误解锁。
- 结论 4:
  - 最近已验收后端 lineage 已包含 Codex warm/resident gate；当前主工作区代码没有。新任务执行必须避开当前 dirty `main`，从已验收基线开新 worktree。

## 风险假设

- 假设:
  - 只有带系统恢复标记的 disabled `codex` auth 才应进入自动恢复扫描。
- 验证方式:

- 验证方式:
