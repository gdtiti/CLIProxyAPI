## 方案摘要

- 推荐方案:
  - 在 `sdk/cliproxy/service_auth_maintenance.go` 里新增“disabled codex recovery”扫描与执行分支，复用现有 maintenance loop 的扫描节奏、路径聚合、watcher 抑制和文件 reload 机制；同时新增内存 recent buffer + append-only JSONL 持久化日志。
- 推荐原因:
  - disabled 恢复属于文件型 auth 的后台维护问题，不属于现有 `core auth auto-refresh` 的活跃 auth 刷新问题。
  - 现有 maintenance loop 已经具备路径聚合、串行写文件、失败重试和 watcher 协调，改动最集中。
  - 结构化 JSONL 日志不依赖 PG/SQLite，新旧部署都能工作。

## 备选方案对比

### 方案 A

- 做法:
  - 扩展 `auth-maintenance`：扫描带系统恢复标记的 disabled `codex` auth；按需 refresh；quota 恢复则 unlock；每一步写结构化恢复日志。
- 收益:
  - 复用现有后台维护框架，路径级去重和文件写入一致性最好。
  - 不依赖 `core auth auto-refresh` 对 disabled auth 的限制。
  - 不需要新的数据库依赖。
- 代价:
  - 需要在 `service_auth_maintenance.go` 增加 recovery candidate、执行分支和日志设施。
  - 需要给 management runtime auto-disable 链补系统恢复标记。
- 风险:
  - 要处理“自动禁用”和“人工禁用”的区分，否则会误解锁。

### 方案 B

- 做法:
  - 修改 `sdk/cliproxy/auth/conductor.go`，让 `core auth auto-refresh` 也扫描 disabled auth，并在 refresh / quota probe 后直接解锁。
- 收益:
  - refresh 逻辑集中在 auth manager。
- 代价:
  - 要改写 `shouldRefresh()` 的 disabled 语义，并处理 Codex warm/resident gate 与 disabled 语义冲突。
  - 无法自然复用现有 file maintenance 的路径聚合与 watcher 保护。
- 风险:
  - 容易把“普通 refresh”和“disabled 恢复”两类逻辑搅在一起，影响面更大。

### 方案 C

- 做法:
  - 新建独立后台 worker 和独立数据库表，专门维护 disabled 恢复与日志。
- 收益:
  - 职责隔离，后续可扩展成完整审计中心。
- 代价:
  - 需要新配置、新生命周期管理、新存储模型。
  - 当前项目没有现成 SQLite 通道，PG 也不是所有部署的硬依赖。
- 风险:
  - 对本轮 required-only 范围明显过重。

## 锁定设计

- 入口模块:
  - `sdk/cliproxy/service_auth_maintenance.go`
  - `internal/api/handlers/management/auth_files_runtime_hook.go`
  - `internal/runtime/executor/codex_executor.go`
  - `sdk/auth/filestore.go`
  - `internal/logging/global_logger.go`
- 关键调用链:
  - 启动: `sdk/cliproxy/service.go -> startAuthMaintenance -> runAuthMaintenance`
  - 扫描: `runAuthMaintenance -> scanAuthMaintenanceCandidates + scanDisabledRecoveryCandidates`
  - 执行: `applyAuthMaintenanceCandidate -> applyDisabledRecoveryCandidate`
  - refresh: `applyDisabledRecoveryCandidate -> CodexExecutor.Refresh`
  - quota probe: `applyDisabledRecoveryCandidate -> usage probe helper -> parseCodexQuotaRetryDecision`
  - 解锁: `merge recovered metadata -> persist auth file -> coreManager.Update/reload`
  - 日志: `record recovery event -> recent memory buffer + append JSONL`
- 数据流:
  1. auto-disable 链在写 `disabled=true` 时，同时持久化系统恢复标记，例如 `auth_maintenance_reason`、`auth_maintenance_disabled_at`。
  2. maintenance scan 只收集 `provider=codex`、`disabled=true`、且带系统恢复标记的 auth。
  3. 若 access token 过期或进入 refresh lead 窗口，调用 `CodexExecutor.Refresh` 生成新 token metadata。
  4. refresh 后或无需 refresh 时，调用 usage probe；若 probe 判断 quota 已恢复，则把 auth 文件改为 `disabled=false` 并清理恢复标记。
  5. 整个过程中，对 scan / skip / refresh / probe / unlock / fail 统一记录结构化事件。
- 错误处理:
  - refresh 失败：保持 disabled，不伪造成功，记录 failure 日志。
  - probe 显示仍限额：保持 disabled，记录 skip/still_limited 日志。
  - `refresh_token_reused`：保持 disabled，标记为不可自动恢复，记录 terminal failure 日志。
  - 文件持久化或 reload 失败：不更新完成态，只记录 failure，并允许下轮重试。
- 配置变更:
  - 本轮不新增独立配置项。
  - disabled recovery 复用 `auth-maintenance.enable` 与 `scan-interval-seconds` 节奏。
  - 恢复日志路径复用 `logging.ResolveLogDirectory(cfg)`，但使用独立 JSONL 文件名，不依赖 `logging-to-file` 开关。

## 分阶段计划

### 阶段 1

- 目标:
  - 落地 disabled recovery candidate、自动恢复标记和结构化日志能力。
- 风险主题:
  - 区分系统自动禁用与人工手动禁用。
- 主要变更:
  - 扩展 auto-disable 链写入恢复标记。
  - 扩展 maintenance scan / execute。
  - 新增 recent buffer + JSONL logger。
- 验证方式:
  - 单元测试覆盖 candidate 过滤、日志写入、refresh 触发条件。
- 完成标志:
  - disabled recovery 的 scan/skip/refresh/fail 都可被测试驱动验证。

### 阶段 2

- 目标:
  - 完成 quota 恢复判定、自动解锁、文件持久化与回归验证。
- 风险主题:
  - 解锁时不能破坏 watcher、reload 和现有 disabled 语义。
- 主要变更:
  - 合并 refreshed metadata。
  - 执行 usage probe 与 unlock。
  - 补齐文档与测试。
- 验证方式:
  - 集成式单元测试覆盖“仍限额保持 disabled”和“额度恢复自动 unlock”两条链。
- 完成标志:
  - 文件与运行态 auth 同步恢复，持久化日志完整。

## 交接与差异分析

- 产品事实源:
  - 用户明确要求：定时检查被禁用账号；AT 需要刷新时自动刷新；额度恢复后自动解锁；动作要有持久化日志。
- 知识事实源:
  - `.devone/wiki/projects/runtime-auth-maintenance.md`
  - `.devone/wiki/patterns/auth-maintenance-runtime-pattern.md`
- 实现事实源:
  - 当前主工作区代码：`sdk/cliproxy/service_auth_maintenance.go`、`sdk/cliproxy/auth/conductor.go`、`internal/api/handlers/management/auth_files_runtime_hook.go`、`internal/runtime/executor/codex_executor.go`
  - 最近已验收后端 lineage：`.devone/worktree/20260408-205635-usage-statistics-visibility-fix` / `gdtiti/main`
- need_communication:
  - no
- 主要差异:
  - wiki 与最近已验收 worktree 已包含 Codex warm/resident refresh gate；当前本地主工作区 `main` 没有这部分代码。
  - 当前实现没有 disabled recovery 动作，也没有 dedicated recovery log。
  - management runtime auto-disable 没有持久化“可自动恢复”标记，重启后无法安全区分手动禁用与系统禁用。
- 待沟通项:
  - 无产品待沟通项；工程上固定采用“只恢复有系统标记的 codex disabled auth”。
- 可直接进入研发的已对齐项:
  - 恢复入口应放在 `auth-maintenance`。
  - refresh/probe 复用已有 Codex executor。
  - 日志做结构化持久化，不走 PG 新子系统。
