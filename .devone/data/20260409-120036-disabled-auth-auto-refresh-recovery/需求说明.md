## 问题定义

- 当前问题:
  - 文件级 `disabled=true` 的 `codex` auth 不会进入 `core auth auto-refresh`，因为 `sdk/cliproxy/auth/conductor.go` 的 `Manager.shouldRefresh()` 开头直接跳过 disabled auth。
  - `sdk/cliproxy/service_auth_maintenance.go` 当前只有“禁用 / 删除”维护动作，没有“disabled auth 自动恢复”动作。
  - `internal/api/handlers/management/auth_files_runtime_hook.go` 的请求数阈值与 quota probe 只作用于当前正在使用的活跃 auth，不会回头扫描已 disabled 的账号。
  - `internal/runtime/executor/codex_executor.go` 已具备 `refresh_token` 刷新能力和 usage API probe 能力，但没有被现有 disabled 恢复链路复用。
  - 项目已有通用文本日志与 usage PG 持久化，但没有专门记录“disabled auth 自动恢复动作”的结构化持久化日志。
- 影响对象:
  - 被 `usage_limit_reached`、`429`、quota/backoff 等原因禁用的文件型 `codex` auth。
  - 需要靠 `refresh_token` 续期 access token 的 disabled 账号。
  - 运维侧对“为什么没恢复 / 什么时候恢复 / 恢复动作是否执行过”的排查。
- 触发背景:
  - 用户要求后台定时检查被禁用账号；AT 需要刷新时自动刷新；额度恢复后自动解锁；并保留持久化日志。
  - 已有调研确认：现状不存在这条自动恢复链路，disabled 文件账号会长期停留在禁用状态，除非人工 PATCH 或重新登录。
- 为什么现在处理:
  - 当前需要人工逐个检查并解锁 disabled 账号，恢复成本高，且没有结构化审计痕迹。
  - 继续沿用现状会让“额度已恢复但账号仍停留 disabled”的问题持续累积。

## 目标与成功标准

- 目标 1:
  - 在现有 `auth-maintenance` 后台维护循环中，定时扫描“可恢复的 disabled 文件型 codex auth”。
- 目标 2:
  - 当 access token 已过期或临近过期、且存在可用 `refresh_token` 时，后台自动执行 refresh。
- 目标 3:
  - 当 usage/quota probe 证明额度已恢复时，自动把 auth 文件从 `disabled=true` 恢复为可用状态，并同步运行态 auth。
- 目标 4:
  - 对 scan / refresh / probe / unlock / skip / failure 产生结构化日志，并落盘持久化。

## 范围边界

- 复用现有 `CodexExecutor.Refresh` 与 usage probe 逻辑，不新造刷新协议。
- 为自动禁用与自动恢复补齐可持久化的恢复标记与动作日志。

- 不自动恢复“人工手动禁用且没有系统恢复标记”的 auth。

## 验收真相陈述

- [REQ-001] 存在恢复标记的 disabled 文件型 `codex` auth，会被后台维护循环定期扫描，而不是永远停留在 disabled。
- [REQ-002] 当 access token 需要刷新且 `refresh_token` 可用时，后台会自动 refresh，并把新 token 信息写回 auth 文件。
- [REQ-003] 当 usage probe 证明额度窗口已经恢复时，后台会自动把 auth 文件 `disabled=false`，并把运行态 auth 恢复为 active。
- [REQ-004] 每次 scan / refresh / probe / unlock / skip / failure 都会写入结构化持久化日志；服务内还保留最近一批内存事件供后续排查。
- [REQ-005] 手动禁用且没有系统恢复标记的 auth 不会被这轮自动恢复逻辑误解锁。

## 约束与依赖

- 技术约束:
  - 当前项目的 `core auth auto-refresh` 明确跳过 disabled auth，不能把恢复逻辑直接塞进现有 `shouldRefresh()` 主链里。
  - 当前项目没有现成的 SQLite 依赖，也没有通用业务事件表；`internal/usage/*` 的 PG 持久化只服务 usage 统计。
  - `sdk/auth/filestore.go` 读写 auth 文件时只依赖 `metadata + disabled`，不会自动持久化 `StatusMessage`；因此自动恢复资格不能只靠运行态 status message。
- 业务约束:
  - 需要区分“系统自动禁用，可自动恢复”和“人工手动禁用，不应自动恢复”。
  - disabled 恢复不能破坏现有 watcher / reload / distributed sync 链路。
- 外部依赖:
  - 依赖 `CodexExecutor.Refresh` 的 `refresh_token` 刷新能力。
  - 依赖 `/backend-api/wham/usage` probe 的可用性来判断 quota 是否恢复。
