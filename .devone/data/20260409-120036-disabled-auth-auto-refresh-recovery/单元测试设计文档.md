## 测试目标

- 需要被保护的核心行为:
  - disabled recovery 只处理带系统恢复标记的 `codex` 文件 auth。
  - access token 需要刷新时会调用 refresh，并持久化新 token。
  - quota 仍未恢复时 auth 保持 disabled。
  - quota 恢复时文件和运行态都会解除 disabled。
  - 每次动作都写入 recent memory buffer 和 JSONL 持久化日志。
- 这轮必须覆盖的失败模式:
  - 手动禁用 auth 被误解锁。
  - `refresh_token_reused` 被错误当成可恢复。
  - refresh 成功但文件没有更新。
  - unlock 成功但日志没落盘。

## 单元测试设计

### UT-001

- 目标:
  - 验证 recovery candidate 过滤条件。
- 覆盖函数/模块:
  - disabled recovery candidate builder / scanner
- 输入:
  - 带系统恢复标记的 disabled codex auth
  - 手动禁用但无恢复标记的 auth
  - 非 codex auth
  - 缺少 refresh_token 的 auth
- 预期输出:
  - 仅系统标记的 disabled codex auth 进入恢复候选
- 失败表现:
  - 手动禁用或非 codex auth 被纳入恢复队列

### UT-002

- 目标:
  - 验证 access token 过期或进入 refresh lead 时会调用 `CodexExecutor.Refresh`。
- 覆盖函数/模块:
  - recovery execute path
  - refresh necessity helper
- 输入:
  - disabled codex auth，`expired` 已过期或接近过期，且有 `refresh_token`
- 预期输出:
  - refresh 被触发
  - 更新后的 token metadata 被写回 auth 文件/内存对象
- 失败表现:
  - refresh 未触发，或 token 未持久化

### UT-003

- 目标:
  - 验证 quota 未恢复时保持 disabled，并写 still_limited / skip 日志。
- 覆盖函数/模块:
  - usage probe 判定
  - recovery logger
- 输入:
  - probe 返回仍受限的 usage body / retryAfter
- 预期输出:
  - auth 仍为 disabled
  - 生成结构化日志事件
- 失败表现:
  - auth 被误解锁，或无日志记录

### UT-004

- 目标:
  - 验证 quota 恢复后自动 unlock。
- 覆盖函数/模块:
  - unlock path
  - auth file persist + runtime update
- 输入:
  - probe 返回已恢复的 usage body
- 预期输出:
  - auth 文件 `disabled=false`
  - 运行态 auth `Status=active`
  - 恢复标记被清理
  - 记录 unlock 日志
- 失败表现:
  - 文件与运行态状态不一致

### UT-005

- 目标:
  - 验证 `refresh_token_reused` 或 refresh failure 时不会误解锁。
- 覆盖函数/模块:
  - refresh failure branch
- 输入:
  - `CodexExecutor.Refresh` 返回 `refresh_token_reused`
  - `CodexExecutor.Refresh` 返回普通错误
- 预期输出:
  - auth 保持 disabled
  - 记录 terminal / failure 日志
- 失败表现:
  - auth 被错误恢复，或失败原因丢失

### UT-006

- 目标:
  - 验证 recovery 日志 recent buffer 与 JSONL 文件行为。
- 覆盖函数/模块:
  - recovery logger
- 输入:
  - 多种 recovery event 顺序写入
- 预期输出:
  - recent buffer 保留最新 N 条
  - JSONL 文件按追加顺序持久化
- 失败表现:
  - 顺序错乱、字段缺失、覆盖旧记录

## 属性测试设计

### PT-001

- 性质:
  - recovery candidate 过滤对 provider / disabled / marker / refreshability 的组合保持稳定。
- 输入空间:
  - `provider ∈ {codex, claude, gemini}`
  - `disabled ∈ {true,false}`
  - `system_marker ∈ {true,false}`
  - `refresh_token ∈ {present,absent}`
  - `refresh_disabled_reason ∈ {empty,reused}`
- 不变量:
  - 只有 `provider=codex && disabled=true && system_marker=true && refresh_disabled_reason!=reused` 才可能进入恢复链。
- 预期失败模式:
  - 任一非目标组合被接受

### PT-002

- 性质:
  - 日志写入是 append-only，不会因为重复 scan 覆盖历史。
- 输入空间:
  - 多组 recovery event 顺序、重复事件、失败后重试事件
- 不变量:
  - JSONL 文件行数单调增加
  - recent buffer 只截断最旧记录，不改写已有事件字段
- 预期失败模式:
  - 覆盖、乱序、字段漂移

## 测试夹具与数据策略

- 夹具:
  - 临时 auth 目录
  - stubbed `CodexExecutor`
  - stubbed usage probe 返回体
  - 临时 recovery log 目录
- 真实数据策略:
  - 使用真实 auth metadata 结构字段名：`access_token`、`refresh_token`、`expired`、`account_id`

  - 不用仅靠内存对象断言“已恢复”，必须同时核对 auth 文件内容
  - 不用只断言普通文本日志，必须核对结构化 JSONL 内容
