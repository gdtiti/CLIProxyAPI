## 方案摘要

- 推荐方案:
  - 采用“选择性吸收 + 分阶段落地 + 每阶段验收后合并主线”的方式推进。
  - 每个阶段只处理一个主题，先在 worktree 分支实现，再回主线 `main` 合并、提交、推送。
  - 不直接复制目标仓库整文件，而是对照当前主线实现逐点移植，优先复用现有抽象与测试体系。
- 推荐原因:
  - 当前仓库已经在 Codex、AuthMaintenance、Responses 兼容等方向积累了较多主线特有逻辑，整文件替换风险高。
  - 分阶段实施能把回归面压缩到单个主题，并满足用户“每阶段合并主工作区、提交、推送”的要求。

## 备选方案对比

### 方案 A

- 做法:
  - 直接把目标仓库对应文件或 commit 大片段拷贝/搬运进当前仓库。
- 收益:
  - 速度快，初始实现成本最低。
- 代价:
  - 需要后补大量冲突修复。
- 风险:
  - 极易覆盖当前仓库已有兼容修复，且难以保证每阶段边界清晰。

### 方案 B

- 做法:
  - 按四个主题逐阶段重建实现，并保留当前仓库已知关键行为。
- 收益:
  - 交付边界清晰，适合阶段验收、阶段合并与阶段推送。
- 代价:
  - discovery 与验证工作量更大。
- 风险:
  - 如果任务包、测试与阶段记录不持续回写，容易在长流程中失真。

## 锁定设计

- 入口模块:
  - 阶段 1：
    - `internal/config/config.go`
    - `config.example.yaml`
    - `sdk/cliproxy/builder.go`
    - `sdk/cliproxy/service.go`
    - `sdk/cliproxy/auth/*`
  - 阶段 2：
    - `internal/translator/codex/openai/chat-completions/*`
    - 相关 translator/executor 测试
  - 阶段 3：
    - `internal/config/sdk_config.go` 或等价配置入口
    - `internal/audit/*`
    - `sdk/cliproxy/builder.go`
    - `sdk/cliproxy/auth/conductor.go`
  - 阶段 4：
    - `internal/runtime/executor/codex_executor.go`
    - `internal/runtime/executor/codex_websockets_executor.go`
    - 对应测试
- 关键调用链:
  - 阶段 1：`config -> builder/service selector wiring -> auth.Manager/conductor -> selector feedback / blocker`
  - 阶段 2：`OpenAI Chat Completions request -> translator -> Codex Responses payload`
  - 阶段 3：`request-audit config -> builder hook -> conductor audit context -> async sink`
  - 阶段 4：`Codex request build -> HTTP/WS header assembly -> upstream request`
- 数据流:
  - 阶段 1 把路由配置与请求特征元数据带入 selector。
  - 阶段 2 把原始请求解析为内存结构，复用缓存并最终单次 `json.Marshal`。
  - 阶段 3 把请求/响应上下文压缩后异步发给外部 endpoint。
  - 阶段 4 把 HTTP/WS 请求头与 turn metadata 调整为更接近目标客户端的形态。
- 错误处理:
  - 路由阶段对 invalid request blocker 只阻断已确认可复现的无效请求体，不扩大到普通错误。
  - translator 阶段出现兼容冲突时，以当前主线已验证行为优先。
  - request-audit hook 失败只能显式 warning，不得影响主请求成功路径。
  - header 拟真阶段不得以破坏现有请求链路为代价换取“更像目标客户端”。
  - 运行态 auth 维护新增保护性约束：`429` 与 quota exceeded 账号统一改为 disable，不再进入 delete；`delete-status-codes` 中的 `429` 视为 disable，`delete-quota-exceeded` 保留字段名仅作兼容。
- 配置变更:
  - 阶段 1 新增/扩展 `routing.strategy`、`routing.success-rate`、`routing.simhash`
  - 阶段 3 新增 `request-audit`
  - 阶段 2 与阶段 4 原则上不新增强制配置，但文档中仍需给出示例
