## 方案摘要

- 推荐方案:
  - 保持第一波 `LastUsedAt/WarmUntil/ResidentUntil` 抽象不变，在 manager 选路完成后通过一个通用的“background refresh hints”桥接层，把 SimHash selector 当前虚拟池成员映射到 `ResidentUntil`。
  - SimHash selector 只暴露“哪些 auth 当前应被视为 resident”的抽象提示；真正写入 `ResidentUntil` 仍由 manager 在受控位置完成。
- 推荐原因:
  - 既满足“虚拟池进入常驻可作为刷新条件”的诉求，又避免 `shouldRefresh()` 或 refresh loop 直接读取 selector 私有成员表。
  - 能在不引入新持久化 schema 的前提下，把 preheat/resident 语义收口到通用热度字段。
  - 相比直接在 selector 内部改写 auth 运行态，这种方案的并发边界更清晰：selector 负责给 hint，manager 负责持有锁并写状态。

## 备选方案对比

### 方案 A

- 做法:
  - 定义 selector -> manager 的 resident hint 抽象；SimHash selector 根据当前虚拟池成员返回 resident auth ID 列表。
  - manager 在选路成功后、克隆返回 auth 前，持锁把对应 Codex auth 的 `ResidentUntil` 延长到 resident window。
- 收益:
  - 最小耦合；refresh 判定继续只依赖 `Auth` 的通用热度字段。
  - 可同时兼容 legacy pick、scheduler fast path、mixed pick，只要它们最终都走 manager 的“选路完成”收口点。
- 代价:
  - 需要给 selector 增加一层轻量接口，并调整 pick 后的 manager 收口逻辑。
- 风险:
  - 若 resident hint 过滤不严，mixed/provider 混合场景可能错误标记非目标 auth，需要在 manager 侧再次按 provider 过滤。

### 方案 B

- 做法:
  - 直接在 `SimHashSelector.Pick()` 内部改写 `Auth.ResidentUntil` / `WarmUntil`。
- 收益:
  - 代码路径短，修改文件少。
- 代价:
  - selector 需要直接写共享 auth 运行态，和 manager 锁边界交叉。
- 风险:
  - 容易产生并发语义不清、后续 selector 复用困难的问题，也更接近“直接依赖私有 pool 实现细节”。

## 锁定设计

- 入口模块:
  - `sdk/cliproxy/auth/simhash_selector.go`
  - `sdk/cliproxy/auth/conductor.go`
  - `sdk/cliproxy/auth/types.go`
  - `sdk/cliproxy/auth/simhash_selector_test.go`
  - `sdk/cliproxy/auth/conductor_background_refresh_test.go`
- 关键调用链:
  - `Manager.pickNext*()` / mixed pick -> selector 选中 auth -> manager 收集 selector background refresh hint -> 写入 `ResidentUntil` -> 后续 `Manager.shouldRefresh()` 消费 resident gate。
- 数据流:
  - `SimHashSelector` 仍独占维护 `pool.members`、`everFilled`、`preferredOutsiderID`。
  - selector 只对外暴露 resident hint，不暴露内部成员表引用。
  - manager 持锁把 resident hint 映射到 `Auth.ResidentUntil`；`shouldRefresh()` 继续只读 `Auth` 热度字段。
- 错误处理:
  - 只对 `provider=codex` 的 auth 应用 resident bridge；mixed 场景必须按当前 auth provider 二次过滤。
  - 若 selector 不支持 resident hint，manager 保持现状，不做隐式 fallback 扩刷。
- 配置变更:
  - 本轮不新增全局 YAML 配置。
  - resident window 优先复用 auth metadata/attributes 的局部 override；若未设置，默认沿用 Codex warm window 的 1h 作为 resident 窗口。
