## 问题定义

- 当前问题:
  - 第一波改造已经让 Codex 后台 refresh 变成 `lead + warm/resident gate`，但 resident 仍只是预留字段，尚未接入真实上游信号。
  - 当前 `SimHashSelector` 已有虚拟池/准常驻池语义：成员进入 `pool.members` 后会在 admission cooldown 内保持池稳定；但这份状态只存在 selector 私有结构，尚未桥接到 `Auth.ResidentUntil`。
  - 结果是：真实请求成功可把 auth 变 warm，但“被虚拟池选中作为预热成员”的 Codex auth 仍不会触发后台 refresh，和用户希望的“用到的或预热的证书才刷新”不完全一致。
- 影响对象:
  - `sdk/cliproxy/auth/simhash_selector.go` 的虚拟池 admission / member 维护路径。
  - `sdk/cliproxy/auth/conductor.go` 的选路后运行态热度写入路径。
  - 已落地的 Codex background refresh gate 是否能正确消费 resident 信号。
- 触发背景:
  - 用户在第一波验收后明确要求继续，把“虚拟池进入常驻”真正作为刷新条件输入。
  - 代码调研确认 `SimHashSelector.pool.members` 具备 resident 语义，但目前没有桥接层。
- 为什么现在处理:
  - 第一波已 accepted 但尚未 closeout；当前 worktree 中已有 warm/resident 基础字段，继续第二波桥接改动成本最低。
  - 若此时不补 resident 桥接，warm gate 只能覆盖“已成功使用”场景，仍无法支撑预热池的主动保活。

## 目标与成功标准

- 目标 1:
  - 把 SimHash 虚拟池成员关系桥接为 Codex resident refresh 信号，而不是直接让 refresh 逻辑读取 selector 私有成员表。
- 目标 2:
  - 保持第一波 `LastUsedAt/WarmUntil/ResidentUntil` 抽象不变，只补充可验证、最小耦合的 resident bridge。
- 成功标准:
  - [REQ-001] 经过 SimHash selector 选路后，进入虚拟池的 Codex auth 能获得非零 `ResidentUntil`，并在 resident 窗口内允许后台 refresh。
  - [REQ-002] resident bridge 不要求改动 auth 文件 schema，不让 `Manager.shouldRefresh()` 直接依赖 `SimHashSelector.pool.members` 私有实现细节。
  - [REQ-003] 既有 disabled / temporary disable / cold auth 语义不退化；非 resident auth 不会被错误扩刷。
