## 测试目标

- 需要被保护的核心行为:
  - SimHash 虚拟池成员能把 Codex auth 标记为 resident，而不是只有成功请求才能参与后台 refresh。
  - resident bridge 不破坏既有 cold / disabled / shouldRefresh 语义。
- 这轮必须覆盖的失败模式:
  - 选路后 `ResidentUntil` 没写入。
  - manager 直接依赖 selector 私有成员表，导致接口缺位无法测试。
  - mixed/provider 过滤失误，把非 Codex auth 也错误标为 resident。

## 单元测试设计

### UT-001

- 目标:
  - 验证 SimHash selector 选路后，manager 会给进入虚拟池的 Codex auth 写入 `ResidentUntil`。
- 覆盖函数/模块:
  - `Manager.pickNextLegacy`
  - resident hint 收口逻辑
  - `SimHashSelector`
- 输入:
  - `PoolSize=2` 的 SimHash selector
  - 两个可用 Codex auth
- 预期输出:
  - 选中的 auth 返回正常
  - manager 内部对应 auth 的 `ResidentUntil` 非零且晚于当前时间
- 失败表现:
  - `ResidentUntil` 仍为零，或 selected auth 缺失

### UT-002

- 目标:
  - 验证 resident bridge 会按当前虚拟池成员批量续期，而不是只触发单个 selected auth。
- 覆盖函数/模块:
  - `SimHashSelector` resident hint
  - manager resident 应用逻辑
- 输入:
  - 先把 pool 填满，再触发一次新的 SimHash 选路
- 预期输出:
  - 当前 pool 中的同 provider 成员都具有非零 `ResidentUntil`
- 失败表现:
  - 只有 selected auth 被标记 resident，其余 pool member 未续期

### UT-003

- 目标:
  - 验证 resident bridge 产出的 resident heat 可被 `shouldRefresh()` 消费。
- 覆盖函数/模块:
  - `Manager.shouldRefresh`
  - resident window helper
- 输入:
  - 命中 lead 的 Codex auth，先冷态再经 resident bridge 标记 resident
- 预期输出:
  - 冷态时 `shouldRefresh=false`
  - 被标记 resident 后 `shouldRefresh=true`
- 失败表现:
  - resident 写入后仍无法触发 background refresh

## 属性测试设计

### PT-001

- 性质:
  - resident bridge 只能放宽被显式 resident 的同 provider auth，不应把任意 auth 统统放宽。
- 输入空间:
  - 不同 provider、不同 pool member 集合、selectedID 是否属于池成员
- 不变量:
  - 非 Codex auth 不因本轮 bridge 改变 refresh 语义
  - disabled auth 即使 resident 也不应进入 shouldRefresh
- 预期失败模式:
  - provider 过滤失效，或 disabled 语义被 resident 覆盖
