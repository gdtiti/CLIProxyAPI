## 方案摘要

﻿- 推荐方案: 批量上传支持多文件与 zip 两种输入 + staging 校验导入，可配置“全有或全无/允许部分成功”；启动优化优先合并多次全量扫描并复用解析结果，同时把 store 同步/模型拉取/管理面更新/Kiro 刷新/usage 初始化拆为可配置的延后或异步；补充 401 自动处置与配额为 0 的自动禁用策略。
- 推荐原因: 对现有单文件接口侵入小、可验证性强；先压缩重复扫描与阻塞型外部依赖，风险可控；自动处置减少故障扩散。
- 优先范围: Codex 认证文件字段校验/补齐（access_token + account_id）与冷却刷新路径；其余 provider 先按现有 Retry-After/退避策略执行。

## 备选方案对比

### 方案 A

- 做法: 新增批量上传入口（支持 zip 与 multipart 多文件），服务端 staging 统一校验与写盘；可配置原子性与部分成功；批量持久化到 store 后统一 reload；新增 401 自动处置与配额 0 自动禁用策略。
- 收益: 一次导入，多文件一致性更好；可显著降低管理端重复调用与启动前的手工整理成本；故障自动化处置降低人工介入。
- 代价: 实现复杂度与错误处理成本上升；需要限制包大小与单次文件数量；需要更多测试覆盖。
- 风险: 原子性与部分成功策略不清会反复改动；大包导致内存/超时；处置策略不清导致误删/误禁用。

### 方案 B

- 做法: 上传 zip 后生成异步导入任务（后台逐批写入 authDir + store），提供进度查询；自动处置以后台任务形式执行。
- 收益: 大批量导入体验最好，长任务可控。
- 代价: 需要任务队列/状态管理；跨模块改动更多。
- 风险: 任务一致性与失败恢复复杂，需较多测试投入。

### 方案 C

- 做法: 不新增后端批量能力，仅提供 CLI/脚本批量调用现有单文件 `POST /auth-files`；自动处置仅做人工流程指引。
- 收益: 改动最小，风险最低。
- 代价: 仍需多次调用；一致性弱；性能改善有限；自动化处置不足。
- 风险: 仍会触发多次 reload，启动问题不解决。

## 锁定设计

﻿- 入口模块: `internal/api/handlers/management/auth_files.go`（新增批量 handler），`internal/api/server.go`（新增路由）。
- 关键调用链: 批量上传 -> staging 校验 -> 写入 authDir -> 批量持久化 store（可选）-> 统一 reload（可选）。
- 数据流: 请求包 -> 临时目录 -> 校验通过文件集 -> 目标 authDir -> store。
- 错误处理: 支持全有或全无与允许部分成功两种策略；无论哪种都返回逐文件结果清单。
- 配置变更: 最大文件数/包体大小/原子性策略/是否自动 reload。
- 自动处置: 401 触发阈值为“10 分钟内连续 3 次”，且需可配置；Gemini 先删虚拟凭证，全部虚拟凭证清空后才删真实凭证；配额为 0 且需冷却时自动禁用，冷却时间以配额查询返回为准，冷却到期自动恢复。
- 配额/冷却差异: Codex 429 -> usage API 解析 reset_after_seconds/reset_at（rate_limit/code_review_rate_limit，窗口 five_hour/weekly）；Qwen quota 403->429 冷却至北京时间次日 00:00；Gemini CLI / Antigravity 解析 RetryInfo.retryDelay 或 ErrorInfo.metadata.quotaResetDelay；Kiro 使用内部冷却计算（1-5 分钟指数，suspended 可 24h）；Gemini/Gemini Vertex/Claude/GitHub Copilot/Kimi/Kilo/iFlow/AIStudio/OpenAICompat 未检索到 Retry-After 解析，走 conductor 指数退避。
- Codex 认证文件要求: 需包含 access_token 与 account_id；account_id 可由 jwt_parser 的 chatgpt_account_id 提取；缺失时冷却刷新退化为错误体解析/退避。
- 优先实现顺序: 先 Codex 认证文件配合 + 冷却刷新，再扩展其他 provider 的细化策略。
- 启动优化切点: store Bootstrap/同步、watcher 初次全量扫描、模型列表拉取、管理面更新、Kiro 刷新、usage 初始化。
