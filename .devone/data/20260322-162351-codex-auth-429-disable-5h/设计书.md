## 方案摘要

- 推荐方案: 在 `sdk/cliproxy/auth` 中引入“临时禁用”元数据与辅助函数；当 `AuthManager` 记录 `codex` 的 429 结果时，把整份 auth 标记为“临时禁用到当前时间 + 5h”，同时把 auth/global model/current model 的恢复时间统一写为 5 小时；选择器和 scheduler 通过该元数据把 auth 视为可自动恢复的冷却态。
- 推荐原因: 复用现有 `MarkResult -> persist -> runtime_persistence -> selector/scheduler` 主链，改动集中、重启可恢复、且不会把 auth 永久从调度结构中删除。

## 备选方案对比

### 方案 A

- 做法: 使用 `auth.Status=disabled` + 临时禁用到期时间元数据，不设置 `auth.Disabled=true`；选择器把“临时禁用中的 disabled”解释为 cooldown，到期后自动放行。
- 收益: 满足“禁用 5 小时”的展示语义，又保留自动恢复能力；不需要新增独立后台清理线程。
- 代价: 需要在 `AuthManager`、selector 和测试中增加少量分支。
- 风险: 若有其它代码路径直接把 `StatusDisabled` 当永久禁用，需要同步放宽或在 user-facing clone 上做归一化。

### 方案 B

- 做法: 直接把 `auth.Disabled=true` 和文件 `disabled=true` 持久化 5 小时后再恢复。
- 收益: 语义最直观，和人工禁用字段一致。
- 代价: scheduler 会直接移除该 auth，需要额外的恢复机制和到点回写。
- 风险: 高，容易形成永久禁用或恢复不及时；比当前需求需要更多附带逻辑。

## 锁定设计

- 入口模块: `sdk/cliproxy/auth/conductor.go`
- 关键调用链: `internal/runtime/executor/codex_executor.go` 产出 429/RetryAfter/QuotaWindow -> `sdk/cliproxy/auth/conductor.go:MarkResult` 写回运行时状态 -> `sdk/cliproxy/auth/runtime_persistence.go` 落盘 -> `sdk/cliproxy/auth/selector.go` / `scheduler.go` 跳过并在到期后恢复。
- 数据流: 429 触发后写入 `auth.Metadata` 中的临时禁用到期时间与原因；同时把 auth 和 global model/current model 的 `NextRetryAfter`、`Quota.NextRecoverAt` 统一设置为 `now + 5h`。
- 错误处理: 仅在 `provider=codex && status=429` 时应用；非 429、非 Codex、401/402 等其它错误路径保持现状。
- 配置变更: 无。本次时长固定为 5 小时，不引入新配置项。
