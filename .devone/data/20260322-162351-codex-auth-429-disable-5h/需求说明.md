## 问题定义

- 当前问题: Codex 认证文件在请求上游返回 `429 Too Many Requests` 后，现有逻辑只会把该 auth 标记为配额冷却或模型级不可用，不会把整份 Codex 认证文件立即拉出调度池 5 小时。
- 影响对象: `codex` provider 的认证文件、认证选择器、AuthManager 运行时状态持久化、相关回归测试。
- 触发背景: 用户要求当 Codex 认证文件请求遇到 429 时，直接禁止该认证文件 5 小时，而不是继续参与同轮或短周期内的选择。
- 为什么现在处理: 现有 Codex 429 处理虽然能识别 `five_hour/weekly` 窗口，但不足以满足“整份认证文件直接禁用 5 小时”的调度约束，容易在同一份认证持续被选中时反复触发 429。

## 目标与成功标准

- 目标 1: 当 `codex` 认证文件上的请求遇到 429 时，立即把该 auth 从调度候选中移出，持续 5 小时。
- 目标 2: 5 小时到期后该 auth 自动恢复可选，不需要手工启用，并且重启后仍能保持正确的剩余禁用时间。

## 范围边界

### 本次必须完成

- 调整 Codex 429 结果写回 AuthManager 的逻辑，使其对整份 auth 生效，而不只是当前模型。
- 持久化 5 小时禁用窗口，使进程重启后仍能正确恢复。
- 确保选择器与 scheduler 在禁用期内跳过该 auth，并在到期后自动恢复。
- 补充最小必要测试，覆盖 429 触发、禁用持续时间、禁用期跳过、到期恢复。

### 本次明确不做

- 不修改非 Codex provider 的 429 处理策略。
- 不新增管理 API 或 TUI 开关来人工配置该 5 小时时长。
- 不重构现有 quota cooldown 体系，只在现有链路上做最小增量改动。

## 验收真相陈述

- [REQ-001] `codex` auth 在请求返回 429 后，会被整份 auth 级别地移出调度池 5 小时。
- [REQ-002] 该 5 小时禁用在运行中和重启后都能保持，并且到点后自动恢复，不需要人工启用。

## 约束与依赖

- 技术约束: 不能用 `auth.Disabled=true` 直接永久移出 scheduler，否则无法在 5 小时到点后自动恢复；应复用现有 `NextRetryAfter`、runtime persistence、selector/scheduler 机制。
- 业务约束: 仅针对 `codex` 认证文件；用户明确要求固定 5 小时。
- 外部依赖: 依赖当前 `CodexExecutor` 已能把 429 识别并传递到 `AuthManager.MarkResult` 的能力。

## 风险与待确认项

- 风险: 若继续保留 `StatusDisabled` 但没有区分“临时禁用”和“人工禁用”，会导致 auth 永久不可用。
- 待确认: 按用户要求固定 5 小时执行，即使上游 usage API 返回更长窗口也不延长本地禁用时长。
