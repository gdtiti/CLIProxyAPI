## 问题定义

- 当前问题:
  - 现有 `distributed-sync.enabled` 只控制 notifier / manager 是否启用，但 `PostgresStore` 在 `PersistConfig`、`PersistAuthFiles`、`Save`、`Delete` 里仍会继续写 `sync_versions` / `sync_outbox`，无法仅通过配置暂停分布式记录。
  - 现有 auth 删除是硬删除，且入口分散在 management API、runtime maintenance hook、service maintenance 三条链路，删除后无法恢复，也没有回收站语义。
  - 分布式数据目前没有专门的清理入口，历史 `sync_outbox` 记录和 `sync_versions` 状态无法通过管理能力显式清理。
  - usage 历史虽然已有 PG 清理 worker 与 `DELETE /v0/management/usage`，但保留期现在靠环境变量控制，且删除接口不会清空 `defaultRequestStatistics`，统计仍可能继续膨胀或看起来“没删干净”。
- 影响对象:
  - 多节点部署下需要临时暂停分布式记录、避免继续写入同步历史的运维场景。
  - 通过 management 上传、维护、自动禁用/删除 auth 文件的运维与管理端用户。
  - 长期运行、usage 与 distributed 数据持续积累的服务实例。
- 触发背景:
  - 用户明确要求：通过配置文件暂停分布式相关记录；认证文件删除改成软删除并提供回收站；数据库提供清理分布式数据的能力；历史统计支持清理，避免持续膨胀。
  - 现状调查已确认上述缺口真实存在，不是推测问题。
- 为什么现在处理:
  - 这几项都属于已有能力的运维缺口，继续维持现状会导致数据持续膨胀、误删不可恢复、以及多节点状态管理缺少收敛手段。

## 目标与成功标准

- 目标 1:
  - 新增配置项，允许在不关闭整个 distributed sync 能力定义的前提下，暂停 `sync_versions` / `sync_outbox` 记录。
- 目标 2:
  - 将 auth 删除改造成软删除，删除后进入回收站，并提供恢复与最终清理能力。
- 目标 3:
  - 提供 management / store 层的分布式数据清理能力，至少区分 `sync_outbox` 历史清理与 `sync_versions` 状态重置。
- 目标 4:
  - 将 usage 历史清理能力提升为配置文件驱动，并补齐内存统计清理，避免“数据库删了但内存还在”的假象。
- 目标 5:
  - 保持现有调用链最小改动，不引入静默 fallback，不破坏单机与既有多节点部署的基本行为。

## 范围边界

### 本次必须完成

- `distributed-sync` 新增独立的“记录开关”，并让 `PostgresStore` 写 config/auth 时受其控制。
- auth 删除统一走软删除 / 回收站语义，覆盖 management API、runtime hook、service maintenance 三条现有删除链路。
- 新增回收站读取、恢复、清理能力，以及 distributed 数据清理能力。
- usage retention 从环境变量提升到 YAML 配置，并让手动清理同时清空 HotBuffer 与内存统计单例。
- 补齐最小单元测试 / 定向测试，覆盖配置、删除链路、清理能力和关键回归点。

### 本次明确不做

- 不实现复杂的多版本回收站保留策略、批量恢复审批流或独立审计库。
- 不做 distributed sync 协议升级，不引入新的总线或第二套同步通道。
- 不补整仓所有既有失败测试，只做本轮变更相关的 targeted verification。
- 不做历史 usage 数据压缩归档，只做清理与容量收敛。

## 验收真相陈述

- [REQ-001] 配置层存在显式开关，可暂停 distributed change recording；开关关闭后，config/auth 写路径不再写 `sync_versions` / `sync_outbox`。
- [REQ-002] auth 删除不再直接硬删除，而是统一进入回收站；management API、runtime hook、service maintenance 三条链路行为一致。
- [REQ-003] 管理端可查看、恢复和清理回收站 auth；活动 auth 查询与 reload-from-store 不会把回收站 auth 当成活动记录重新加载。
- [REQ-004] 管理端可清理分布式历史记录，并能区分 outbox 清理与 version 重置，不把高风险动作混成一个默认删除。
- [REQ-005] usage 历史清理由配置文件驱动，且手动清理后 PG、HotBuffer、内存统计三处状态一致收敛。

## 约束与依赖

- 技术约束:
  - 现有 distributed sync 依赖 PostgreSQL `sync_versions` / `sync_outbox` 与 Redis Pub/Sub；manager 通过 `GetDistributedVersions()` 做 reconcile。
  - 现有 auth store 以相对路径 `id` 作为记录主键，适合通过“活动路径 / `.trash` 路径”表达回收站语义。
  - 现有 usage 清理 worker 已存在，但默认保留期来自 `USAGE_RETAIN_DAYS` / `USAGE_AGG_RETAIN_DAYS`。
- 业务约束:
  - 回收站方案必须保证“删除后可恢复”，同时默认不再出现在活动 auth 列表中。
  - 暂停 distributed recording 必须是显式运维行为，不能误导成“功能仍会跨节点传播”。
- 外部依赖:
  - PostgreSQL store、Redis distributed sync、management API 路由、runtime auth manager、usage PG store 与 cleanup worker。

## 风险与待确认项

- 风险:
  - 关闭 distributed recording 后，本地 config/auth 改动不会继续传播到其他节点，这是明确的功能影响。
  - 如果回收站过滤不完整，回收站 auth 可能被 `List()` 或 `syncAuthFromDatabase()` 重新当成活动文件加载。
  - 如果 usage 清理不处理内存统计单例，用户仍会看到历史数据残留。
- 待确认:
  - 当前默认按 `required-only` 推进，优先交付最小可验证能力；更深的历史归档、批量恢复增强和整仓回归暂不纳入本轮。
