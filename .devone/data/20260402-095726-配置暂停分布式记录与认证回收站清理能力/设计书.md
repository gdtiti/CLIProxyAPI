## 方案摘要

- 推荐方案:
  - 采用“配置开关 + 路径型回收站 + 分层清理接口 + usage 配置化清理”的最小改动方案：
    1. 在 `distributed-sync` 下新增独立记录开关，不复用 `enabled`。
    2. auth 删除改为移动到 `.trash/` 并同步更新 store 记录，恢复时再移回活动路径。
    3. distributed 清理拆成 `sync_outbox` 历史清理与 `sync_versions` 状态重置两类接口。
    4. usage retention 升级为 YAML 配置，同时补 `RequestStatistics.Reset()` 或等价能力，保证手动清理后内存与 PG 一致。
- 推荐原因:
  - 这条路线复用现有 `auth_store.id=相对路径` 模型、现有 management 路由与现有 distributed sync 调用链，不需要重做 schema 主干或引入额外服务；同时能把风险行为分层暴露，便于验证与运维说明。

## 备选方案对比

### 方案 A

- 做法:
  - 直接给 auth 表加 `deleted_at` / `trashed_at` 字段；distributed 记录暂停复用 `distributed-sync.enabled`；usage 继续保留 env 驱动。
- 收益:
  - 改数据库语义比较直接，列表过滤容易表达。
- 代价:
  - 与当前 `id -> 相对路径 -> 本地文件` 模型不贴合，既要改 schema 又要处理文件系统状态，侵入更大。
- 风险:
  - 很容易出现“DB 软删了，但磁盘文件还在 / reload 仍会捞起”的双状态不一致问题。

### 方案 B

- 做法:
  - 保留现有 schema 主干，新增 `distributed-sync.recording-enabled`；auth 删除时把文件和 store 记录迁移到 `.trash/`；对活动列表、reload-from-store、恢复、清理分别做路径过滤与操作接口；usage 清理提升为 YAML 配置并补内存 reset。
- 收益:
  - 与现有实现最贴合；文件路径天然可表达“活动区/回收站”；恢复时可直接复用已有写路径与 reload 链路。
- 代价:
  - 需要统一三条删除链路，并补若干管理接口与测试。
- 风险:
  - 如果某条删除链路漏改，仍会发生硬删除；如果路径过滤不严，回收站数据会被当成活动数据。

### 方案 C

- 做法:
  - 保持当前硬删除与 distributed 记录逻辑不变，只额外增加数据库清理接口和 usage retention 配置。
- 收益:
  - 开发量最小。
- 代价:
  - 无法满足“软删除 / 回收站”与“暂停分布式记录”的核心诉求。
- 风险:
  - 只能缓解膨胀，不能解决误删不可恢复与运维开关缺失。

## 锁定设计

- 入口模块:
  - `internal/config/config.go`
  - `config.example.yaml`
  - `internal/store/postgresstore.go`
  - `internal/store/distributed_sync.go`
  - `internal/api/handlers/management/auth_files.go`
  - `internal/api/handlers/management/auth_files_runtime_hook.go`
  - `sdk/cliproxy/service_auth_maintenance.go`
  - `internal/api/handlers/management/usage.go`
  - `internal/usage/logger_plugin.go`
  - `internal/usage/cleanup.go`
  - `internal/api/server.go`
- 关键调用链:
  - `PersistConfig / PersistAuthFiles / Save / Delete -> recordDistributedChangeTx -> sync_versions + sync_outbox`
  - `DeleteAuthFile / removeManagedAuthFile / deleteAuthMaintenanceCandidate -> os.Remove + store.Delete`
  - `DELETE /v0/management/usage -> PGStore.DeleteAll/DeleteBefore + HotBuffer.Reset`
  - `Manager.reconcile -> GetDistributedVersions -> ReloadConfigFromStore / ReloadAuthFilesFromStore`
- 数据流:
  - distributed recording：
    1. 配置打开时，config/auth 真变更继续写 truth table + version/outbox。
    2. 配置关闭时，只保留本地 truth table 写入，不再 bump 分布式版本与 outbox。
  - auth recycle bin：
    1. 删除动作统一改为“移动到 `.trash/` + 更新 store id/path + 禁用运行态”。
    2. 活动列表、reload-from-store、syncAuthFromDatabase 默认忽略 `.trash/`。
    3. restore 时从 `.trash/` 移回活动路径，再走现有 reload / persist 流程。
  - distributed cleanup：
    1. outbox 清理只删除历史事件。
    2. version reset 单独作为高风险动作暴露。
  - usage cleanup：
    1. worker 读取 YAML retention 配置定期清 PG。
    2. 手动清理时同步清 PG、HotBuffer、内存统计单例。
- 错误处理:
  - 回收站移动失败时必须显式报错，不允许假装删除成功。
  - distributed version reset 需要与普通 outbox cleanup 分开，避免误操作。
  - usage 清理若只完成部分状态清空，必须返回失败或明确记录剩余风险。
- 配置变更:
  - `distributed-sync.recording-enabled`
  - `usage-history.cleanup-enabled`
  - `usage-history.detail-retain-days`
  - `usage-history.aggregate-retain-days`
  - `usage-history.cleanup-interval-seconds`
  - （如需要）`usage-history.max-details-per-model`
  - （可选）`auth-recycle-bin.*` 先不强制，默认使用 `auth-dir/.trash`

## 分阶段计划

### 阶段 1

- 目标:
  - 先落地会影响行为语义的主链：distributed recording 开关、auth 回收站统一删除链路、活动过滤与恢复/清理接口。
- 风险主题:
  - 既要统一删除链路，又不能破坏现有 reload/store/sync 路径。
- 主要变更:
  - 配置结构与样例
  - PostgresStore distributed recording 判断
  - auth trash / restore / purge
  - management 路由接线
- 验证方式:
  - 定向 Go 单元测试
  - management handler / store targeted tests
  - 必要的服务编译
- 完成标志:
  - 用户可通过配置暂停 distributed recording；auth 删除进入回收站并可恢复；活动 auth 不会误读回收站。

### 阶段 2

- 目标:
  - 补齐 distributed 数据清理与 usage 历史收敛能力。
- 风险主题:
  - 不能把高风险的 version reset 与普通清理混用；usage 清理后必须保证内存与 PG 一致。
- 主要变更:
  - distributed cleanup API / store helper
  - usage-history YAML 配置
  - cleanup worker 改读配置
  - RequestStatistics reset / detail cap
- 验证方式:
  - cleanup 相关单元测试
  - targeted handler tests
  - `go test` + `go build ./cmd/server`
- 完成标志:
  - distributed / usage 都能显式清理，且删除后状态收敛一致。
