## 问题定义

- 当前问题:
  管理接口 `POST /v0/management/auth-files` 在上传 auth file 时，只把文件写到
  本地 auth 目录并调用 `registerAuthFromFile` 更新当前节点运行态，没有把新文件
  同步写入当前 token store。
- 影响对象:
  使用 PostgreSQL / object store / git store 这类共享或远端 auth store 的部署，
  尤其是多个节点共用同一份 auth store 的场景。
- 触发背景:
  用户通过“上传认证文件”补充了一批 auth files，当前节点接口返回成功，但 PG
  数据库没有刷新，其它读取同一数据库的节点看到的仍然是旧 auth files。
- 为什么现在处理:
  这已经破坏了“管理接口成功 == 共享存储真实更新”的基本契约，继续让前端或其
  它节点依赖这个上传接口会持续制造脏状态和排障噪音。

## 目标与成功标准

- 目标 1:
  `POST /v0/management/auth-files` 无论走 multipart 上传还是 raw JSON 上传，都要
  在请求链路内把新 auth file 同步写入当前 auth store，而不是只落本地镜像目录。
- 目标 2:
  上传成功后当前节点运行态要立即加载到新 auth；如果 store 写入失败，请求必须
  失败，且不能把当前节点运行态留在“已加载但未持久化”的假成功状态。

## 范围边界

### 本次必须完成

- 修复 `UploadAuthFile` 的 multipart 分支与 raw JSON 分支，使其共享同一条
  “校验 -> 写本地镜像 -> 同步写 store -> reload 当前节点”链路。
- 为上传链路补充定向测试，覆盖成功写 store 与持久化失败两条主路径。
- 将本次根因、设计选择、验证证据同步回 DevOne 任务文档包。

### 本次明确不做

- 不改 `POST /v0/management/auth-files/reload-from-store` 的语义。
- 不新增“其它节点自动轮询 PG 并热刷新 auth files”的广播/订阅机制。
- 不把本轮问题扩展成 watcher 全链路重构或多节点配置同步框架重做。

## 验收真相陈述

- [REQ-001] 上传 auth file 成功后，当前 store 中会同步出现对应文件内容，当前
  节点的 `authManager` 也会立即读到该 auth file 的最新运行态。
- [REQ-002] 如果 store 持久化失败，上传接口返回非 200，且不会把当前节点运行态
  留在“已经注册新 auth，但 store 仍旧值”的不一致状态。

## 约束与依赖

- 技术约束:
  继续复用现有 auth store 抽象，不新增新的上传持久化旁路；上传后当前节点的运
  行态刷新仍复用 `registerAuthFromFile -> reloadAuthFile` 既有逻辑。
- 业务约束:
  用户当前只要求修复上传未写 store 的缺陷，并明确聚焦共享数据库下的 auth file
  一致性问题。
- 外部依赖:
  PostgreSQL / object / git store 等后端各自已有 `PersistAuthFiles` 能力；多节
  点是否看到更新，仍依赖其它节点后续主动 reload-from-store 或等价流程。

## 风险与待确认项

- 风险:
  即使上传节点已经把文件写入 PG，其它节点仍然不会凭空自动热刷新；这不是本轮
  新增能力，仍需要后续单独设计自动同步机制。
- 待确认:
  用户后续若希望“上传一个节点，所有节点自动生效”，需要另开需求明确跨节点刷
  新策略，而不是继续把它混进当前上传 bug 修复里。
