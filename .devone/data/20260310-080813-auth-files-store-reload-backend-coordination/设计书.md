## 方案摘要

- 推荐方案:
  为 `UploadAuthFile` 增加共享 helper，把 multipart / raw JSON 两个入口统一为
  “校验 auth JSON -> 写本地镜像 auth file -> 同步调用当前 store 的
  `PersistAuthFiles` -> `registerAuthFromFile` 刷当前节点运行态”。
- 推荐原因:
  上传链路面对的是整份 auth file 原始 JSON，而不是已经构造好的单个运行态
  record；因此同步 `PersistAuthFiles` 比依赖 watcher 异步发现更贴合上传语义，
  也能直接命中 PG raw file upsert 的真实缺口。

## 备选方案对比

### 方案 A

- 做法:
  保持当前实现，只写本地镜像目录并依赖 watcher 异步发现文件变化后再去持久化。
- 收益:
  代码改动最小。
- 代价:
  请求返回成功与 store 真正更新之间存在时序窗口。
- 风险:
  watcher 是否工作、何时工作、是否绑定了正确 store，全都变成上传契约的一部
  分；这正是当前问题的根源。

### 方案 B

- 做法:
  上传 handler 在请求链路内同步写 store；若 store 持久化失败，则恢复上传前的
  本地文件内容并返回错误；写 store 成功后再刷新当前节点运行态。
- 收益:
  请求成功语义清晰，可直接保证“共享 store 已更新 + 当前节点已刷新”。
- 代价:
  需要在 handler 内显式处理文件回滚和校验逻辑。
- 风险:
  其它节点依然不会自动刷新；但这属于既有系统边界，不是本次修复引入的新风险。

## 锁定设计

- 入口模块:
  `internal/api/handlers/management/auth_files.go`
- 关键调用链:
  `UploadAuthFile -> persistUploadedAuthFile -> validateUploadedAuthFile ->
  persistUploadedAuthToStore -> registerAuthFromFile`
- 数据流:
  上传字节流先用 watcher synthesizer 语义做校验，通过后写入镜像 auth dir，再
  同步调用当前 token store 的 `PersistAuthFiles`，最后把当前节点运行态 reload
  到刚写入的文件内容。
- 错误处理:
  如果 auth JSON 无法合成有效 auth，直接失败；如果 store 持久化失败，则恢复上
  传前本地文件并返回错误；只有 store 持久化成功后才允许刷新当前节点运行态。
- 配置变更:
  无新增配置项，继续复用现有 `cfg.AuthDir` 与当前 token store。

## 分阶段计划

### 阶段 1

- 目标:
  修复上传 auth file 不写共享 store 的缺陷。
- 风险主题:
  上传成功与 store 真正落库之间的时序不一致。
- 主要变更:
  `UploadAuthFile` 共用 helper、同步 store persist、失败回滚本地文件、成功后当
  前节点 reload。
- 验证方式:
  management handler 单测覆盖成功与失败路径；完整 management 包测试通过。
- 完成标志:
  上传成功路径能同时看到 persister 被调用与当前节点 authManager 更新；失败路
  径会返回错误并恢复原文件。

### 阶段 2

- 目标:
  形成本轮修复的执行与验收证据。
- 风险主题:
  把“上传未写 store”与“多节点自动刷新”混成一个需求，导致范围失控。
- 主要变更:
  更新 DevOne 文档、记录验证命令、保留后续跨节点自动刷新的范围边界。
- 验证方式:
  文档包与代码、测试结果一致。
- 完成标志:
  R1-R3 都有证据，R4 可进入门禁核对。

## 非目标

- 不新增跨节点自动 reload / push 通知能力。
- 不改 watcher 的 fsnotify 事件模型。
- 不扩展新的 auth file 管理字段。

## 设计评审结论

- 用户是否批准:
  是。用户在同一 `devone` 任务下继续要求排查并修复该上传一致性问题。
- 批准范围:
  修复上传链路未写 store 的后端缺陷，并整理到可提交状态。
- 备注:
  “其它节点自动看到更新”被明确识别为独立能力边界，不在本轮自动展开。
