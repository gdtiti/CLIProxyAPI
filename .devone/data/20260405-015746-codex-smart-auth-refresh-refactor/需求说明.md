## 问题定义

- 当前问题:
  - `core auth auto-refresh` 固定每 `15m` 扫描一次全部 auth，Codex provider 的 `RefreshLead()` 又固定为 `5d`。
  - Codex access token 实际过期时间写在 auth metadata 的 `expired` 字段，寿命远小于 `5d`，导致当前实现几乎每轮扫描都把全部可用 Codex auth 视为刷新候选。
  - 当前 refresh 判定没有“最近使用 / 预热 / 常驻池”门槛，后台刷新压力与真实流量热度脱钩。
- 影响对象:
  - `sdk/cliproxy/auth` 的 refresh conductor 与 selector 调度链路。
  - `codex` 文件型 auth 的后台 refresh 频率、refresh token 消耗、429/disable 风险。
  - 运维侧对 warm auth、cold auth、虚拟池成员的可控性。
- 触发背景:
  - 已完成只读分析任务 `20260405-005348-codex-auth-and-quota-analysis`，确认现状确有“近似 15 分钟全刷”问题。
  - 用户要求把知识沉淀转成落地改造，形成一套更智慧的认证刷新与检查方案，并把虚拟池纳入条件输入。
- 为什么现在处理:
  - 现状会持续增加无效 refresh、提升 refresh_token_reused / 429 / usage_limit_reached 风险。
  - 该问题位于运行态核心调度层，越晚改动越容易和更多 auth 管理策略耦合。

## 目标与成功标准

- 目标 1:
  - 让 Codex 后台 refresh 只覆盖“最近使用或被显式预热”的 auth，而不是每轮扫描全量刷。
- 目标 2:
  - 为后续 resident / 虚拟池 / 健康检查中心保留统一热度字段与扩展点。
- 成功标准:
  - [REQ-001] cold Codex auth 在未被使用、未被预热时，不再因为 `RefreshLead=5d` 而在每轮 `15m` 扫描中进入后台 refresh。
  - [REQ-002] warm Codex auth 在最近使用窗口内仍可正常进入后台 refresh，现有 disabled / temporary disable / next refresh after 行为不退化。
  - [REQ-003] 运行态新增统一热度信号字段，后续可桥接虚拟池 resident/warm 机制，而不直接依赖 selector 私有池结构。
