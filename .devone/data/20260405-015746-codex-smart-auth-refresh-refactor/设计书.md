## 方案摘要

- 推荐方案:
  - 在通用 `Auth` 运行态引入 `LastUsedAt`、`WarmUntil`（必要时预留 `ResidentUntil`）热度字段。
  - 在真实请求成功路径更新热度字段；在 Codex 后台 refresh 判定中新增 warm gate，使 cold auth 不参与固定周期 refresh。
  - 保持 selector 私有虚拟池不直接参与 refresh，只把“入池/命中”作为未来可桥接到热度字段的上游信号。
- 推荐原因:
  - 改动面最小，能先止住 “15m 近似全刷” 的主要问题。
  - 不破坏现有 provider 接口、临时禁用、持久禁用和 quota 处理链路。
  - 后续可继续扩展 resident/warm/probe 状态机，而无需再次改 refresh 的基础抽象。

## 备选方案对比

### 方案 A

- 做法:
  - 在 `Auth` 中增加运行态热度字段；在 `MarkResult()` 成功路径写入热度；在 `shouldRefresh()` 中为 Codex 增加 warm gate。
- 收益:
  - 最快落地，能立即把后台 refresh 从“全量周期性刷新”收敛到“基于热度刷新”。
  - 与现有代码耦合最少，单元测试边界清晰。
- 代价:
  - 第一阶段只覆盖“最近成功使用”热度来源，虚拟池 admission 还未直接打通。
- 风险:
  - 需要为 warm window 选择一个稳妥默认值；若默认值不合适，可能需要后续配置化。

### 方案 B

- 做法:
  - 直接把 `SimHashSelector` 的虚拟池成员作为 refresh 常驻池来源，并同步实现 resident 选举、TTL、健康评分与 quota probe。
- 收益:
  - 理论上功能最完整，可一步到位覆盖 warm/resident。
- 代价:
  - 改动链路长，涉及 selector 私有结构、manager 调度、配置与更多测试。
- 风险:
  - 会把 refresh 逻辑耦合到 selector 实现细节，难以扩展到非 simhash 场景，也不适合 required-only 交付。

## 锁定设计

- 入口模块:
  - `sdk/cliproxy/auth/conductor.go`
  - `sdk/cliproxy/auth/types.go`
  - 相关 selector/refresh 单元测试文件
- 关键调用链:
  - 实际请求成功 -> `Manager.MarkResult(...)` -> 更新 auth 运行态热度字段
  - 后台循环 -> `StartAutoRefresh(..., 15m)` -> `Manager.shouldRefresh(...)` -> warm gate -> provider refresh
- 数据流:
  - auth metadata 中的 `expired` 继续作为过期事实源
  - 新增 `LastUsedAt` / `WarmUntil` 只作为运行态热度信号，不写回 auth 文件 schema
  - 后续若有 resident/virtual-pool 信号，统一桥接到 `WarmUntil` / `ResidentUntil`
- 错误处理:
  - disabled / temporary disabled / `NextRefreshAfter` 仍优先短路
  - warm gate 只收缩 refresh 候选，不改变 refresh 失败后的禁用与冷却语义
- 配置变更:
  - 优先采用保守默认窗口完成第一波；若代码中已有合适配置承载点则复用，否则后续再配置化
