## 问题定义

- 当前问题:
  - 当前 `auth-maintenance` 只支持 `delete-status-codes` 和 `codex usage_limit_reached -> disable`，缺少“按可配置上游状态码直接禁用账号”的通用能力。
- 影响对象:
  - `auth-maintenance` 配置解析
  - `sdk/cliproxy` 运行态维护链路
  - management runtime hook 的禁用语义一致性
  - 配置示例与运行态维护文档
- 触发背景:
  - 用户要求新增一个任务，可以通过配置上游错误码触发禁用账号，而不是删除账号。
- 为什么现在处理:
  - 当前删除和禁用已经分成两条维护链路，继续追加状态码策略时需要明确“何时禁用、何时删除”，否则会让配置语义继续分裂。

## 目标与成功标准

- 目标 1:
  - 在 `auth-maintenance` 下新增 `disable-status-codes` 配置，默认空列表表示关闭。
- 目标 2:
  - 当上游返回命中的 HTTP 状态码时，文件型 runtime auth 会被写成 `disabled=true`，并在运行态中标记为禁用，而不是删除。

## 验收真相陈述

- [REQ-001] `auth-maintenance.disable-status-codes` 可被配置文件正确加载，默认值为空列表，显式值会被保留。
- [REQ-002] 命中 `disable-status-codes` 的上游状态码时，auth 文件会被禁用而不是删除；空列表时不会误禁用 generic 错误码。

## 风险与待确认项

- 风险:
  - 若同一个状态码同时出现在 `disable-status-codes` 与 `delete-status-codes` 中，需要固定优先级，否则行为不确定。
- 待确认:
  - 本轮默认采用“disable 优先于 delete”的保守策略，避免显式配置错误时直接删账号。
