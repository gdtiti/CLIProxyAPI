## 问题定义

- 当前问题: 分析当前项目里 “Codex CLI 风格请求 -> 上游 Codex / Responses API” 的转换逻辑、固定特征、配置注入点与版本指纹；同时识别若想增加更多请求特征、制造更多变化、或持续跟进最新模型/版本信息时，应调整的代码位置与配置项。
- 影响对象: OpenAI 兼容入口、Codex 请求转换器、Codex HTTP/WS 执行器、鉴权选择器、模型注册表、配置系统。
- 触发背景: 用户希望明确当前请求链路的可控面，而不是只知道某一个 handler 或某一个 translator。
- 为什么现在处理: 该链路同时决定了上游请求语义、会话行为、头部指纹、模型可见性与“是否看起来像最新 Codex CLI”，需要先做结构化摸底再决定后续改造。

## 目标与成功标准

- 目标 1: 说明当前 Codex CLI 转 API 的请求逻辑有哪些稳定特征、哪些是硬编码、哪些可由配置覆盖。
- 目标 2: 给出“想增加更多特征/变化”与“想保持最新版本信息”两类需求分别应该优先调整的文件和配置。
