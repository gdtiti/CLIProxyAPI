## 方案摘要

- 推荐方案: 采用“分层解构 + 配置优先”的分析输出。先按入口分流、请求体转换、执行器头部/会话、鉴权与路由、模型目录与刷新五层解释现状；然后把可调节点拆成配置层与代码层两类。
- 推荐原因: 用户关注的是“哪些特征已经固定、哪些地方能继续演化”，按分层输出比按文件罗列更容易直接指导后续改造。

## 备选方案对比

### 方案 A

- 做法: 以配置为主，优先通过 `codex-api-key`、`codex-header-defaults`、`payload`、`oauth-model-alias`、`excluded-models`、`force-model-prefix` 做请求变化和模型暴露控制。
- 收益: 风险低，不需要改核心执行链；适合快速试验。
- 代价: 能改的主要是头部、路由、别名、字段覆盖/过滤，改不了底层转换策略和硬编码版本常量。
- 风险: 如果需求涉及消息重写、工具映射、WS 增量策略，仅靠配置不够。

### 方案 B

- 做法: 修改 translator / executor / registry 代码，直接改变请求结构、头部指纹、会话策略和模型目录。
- 收益: 可控面最大，能真正新增语义特征、变体策略和版本指纹。
- 代价: 需要补测试并承担回归风险。
- 风险: 请求兼容性与下游 OpenAI 兼容层可能一起受影响。

## 锁定设计

- 入口模块:
  - `sdk/api/handlers/openai/openai_handlers.go`
  - `sdk/api/handlers/openai/openai_responses_handlers.go`
  - `sdk/api/handlers/openai/openai_responses_websocket.go`
- 关键调用链:
  - OpenAI 入口 -> `resolveEndpointOverride()` -> request translator -> `ExecuteWithAuthManager()` / `ExecuteStreamWithAuthManager()` -> `auth.Manager` -> Codex executor
  - WS 入口 -> `normalizeResponseCreateRequest()` / `normalizeResponseSubsequentRequest()` -> Auth 选择 -> Codex WS executor
- 数据流:
  - 下游 OpenAI 风格请求先依据模型 `SupportedEndpoints` 做端点重定向，再转换为 Codex / Responses 兼容请求体，然后叠加 thinking/payload/header/session 策略后发送上游。
- 错误处理:
  - handler 统一把执行器错误包装成 OpenAI 风格错误；
  - 流式路径支持 bootstrap retry；
  - WS 路径支持增量输入与历史 output 合并两种模式。
- 配置变更:
  - 当前不执行配置变更，仅确认后续优先调整点。
