## 术语与定义

- 运行态临时禁用: 仅写入运行态/metadata 冷却信息，例如 `temporary_disable_until`，到期后通过快照归一化自动恢复可用。
- 文件级持久禁用: 直接把认证文件写成 `disabled=true` 并 reload 到内存，需显式恢复。
- usage_limit_reached: Codex 上游 429 场景的一种配额耗尽类型，当前项目会优先判定并禁用账号。

## 调研结论

- 结论 1: Codex `access_token` 是否过期，不是靠解析 JWT，而是靠认证文件 metadata 中的过期时间字段；Codex 文件实际使用的是 `expired`。
- 结论 2: 当前实现下，Codex 近似每 15 分钟尝试一次后台刷新，而不是只在临近过期前几分钟刷新；原因是 `RefreshLead=5d` 远大于 access token 常见寿命。
- 结论 3: 429 / usage_limit_reached 后，运行态会先做 5 小时临时禁用；management hook 和 service maintenance 还能把文件持久禁用。
- 结论 4: 运行态临时禁用会自动恢复；文件级持久禁用不会自动恢复，只能用管理接口或重新登录恢复。
- 结论 5: `auth-maintenance.enable` 明确控制 service maintenance loop，但 management runtime hook 当前代码中未见受该开关显式拦截。
- 结论 6: `disable-codex-usage-limit-reached` 配置已在 service maintenance 使用，但 management runtime hook 当前没有读取该开关。

## 风险假设

- 假设: Codex access token 的 `expires_in` 通常短于 5 天，因此会导致服务每次 15 分钟扫描都满足刷新条件。
- 验证方式: 已从 `openai_auth.go` 确认 `expired = now + expires_in`，并从 `conductor.go` 确认 `time.Until(expiry) <= RefreshLead` 即刷新。
