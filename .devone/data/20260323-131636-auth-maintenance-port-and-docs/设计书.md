## 方案摘要

- 推荐方案:
  - 采用“结构借鉴、策略兼容”的移植方案：借鉴参考仓库 `AuthMaintenance` 的队列、分组、节流、扫描和 watcher 自抑制实现，但保留当前项目的策略边界，让 `usage_limit_reached` 继续走禁用语义。
- 推荐原因:
  - 这样既能补齐运行态维护能力和稳定性，又不会把参考仓库的 `429 -> delete` 策略误带入当前项目。

## 备选方案对比

### 方案 A

- 做法:
  - 直接照搬参考仓库 `AuthMaintenance` 与 watcher 实现。
- 收益:
  - 实现速度快，结构与参考仓库最接近。
- 代价:
  - 需要大面积替换当前 watcher 和 `Service` 逻辑。
- 风险:
  - 高概率回退当前项目 `usage_limit_reached` 禁用语义，也可能破坏已有 `Kiro`、`distributed sync`、reload 逻辑。

### 方案 B

- 做法:
  - 手工合并参考仓库中的 watcher 稳定性增强与维护队列；策略层继续沿用当前项目的 `AuthRuntime` 规则，并增加 `AuthMaintenance` 作为后台机制与扩展配置。
- 收益:
  - 可最大程度保留当前行为，同时把运行态能力补齐。
- 代价:
  - 需要自己整合行为边界并补测试。
- 风险:
  - 需要认真处理 management hook 与 service hook 的职责分工。

## 锁定设计

- 入口模块:
  - `sdk/cliproxy/service.go`
  - `internal/watcher/watcher.go`
  - `internal/watcher/events.go`
  - `internal/config/config.go`
- 关键调用链:
  - 请求执行结果 -> `coreauth.Manager` hook -> `AuthMaintenance` 结果处理 -> 入队 -> 后台 worker -> 禁用/删除 auth -> watcher 增量刷新
  - 内部 auth 文件改写/删除 -> watcher suppression / debounce -> 增量重载 -> 避免重复处理
- 数据流:
  - `AuthRuntime` 继续承载 `401` 阈值与窗口策略。
  - `AuthMaintenance` 新增承载后台扫描、节流与扩展删除条件。
  - 对 `usage_limit_reached` 解析只产生 disable candidate，不产生 delete candidate。
- 错误处理:
  - 文件删除失败或 token store 删除失败时显式记录错误，并保留重试空间。
  - 普通 `codex 429` 不进入禁用/删除路径。
- 配置变更:
  - 新增 `auth-maintenance` 配置块。
  - 保留 `auth-runtime` 现有字段，不做破坏性迁移。

## 分阶段计划

- 目标:
  - 补齐 watcher 稳定性增强与配置结构。
- 风险主题:
  - watcher 与当前项目已有自动重载能力的兼容性。
- 主要变更:

  - 增加 `AuthMaintenanceConfig` 与默认值整理。
- 验证方式:
  - watcher 单测
  - config 单测
- 完成标志:

- 风险主题:

- 主要变更:

  - 增加删除/禁用 candidate 分流。

- 验证方式:
