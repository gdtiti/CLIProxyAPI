## 方案摘要

- 推荐方案:
  - 保留所有现有配置字段与管理删除接口；仅把自动维护链路中的 delete action / `removeManagedAuthFile` 调用统一替换为 disable action / `handleManagedAuthDisable`。
- 推荐原因:
  - 用户要求是“禁用而不是删除”，不是“删除能力下线”；复用已有禁用写盘与运行态禁用能力，改动面最小且更容易验证。

## 备选方案对比

### 方案 A

- 做法:
  - 将 `service_auth_maintenance`、`auth_files_runtime_hook` 中所有自动删除分支改为自动禁用；保留 `DELETE /auth-files` 与 recycle-bin 入口作为唯一删除路径。
- 收益:
  - 直接满足“自动只禁用、远程接口才可删”的规则。
  - 兼容字段名与运维入口都不变，外部配置/调用方无需改接口名。
- 代价:
  - 需要同步调整测试、注释和运行态维护文档。
- 风险:
  - 需要处理历史 `pending delete` 元数据，否则旧状态仍可能被后台扫描推进。

### 方案 B

- 做法:
  - 删除或废弃 `delete-status-codes` / `codex-max-request-count` / `codex-quota-check-request-interval` 等字段与逻辑。
- 收益:
  - 逻辑表面上更简单。
- 代价:
  - 直接违反“只允许禁用而不是删除，不是删除配置/能力”的要求。
  - 会破坏现有配置兼容性。
- 风险:
  - 用户已有配置和使用习惯被破坏，改动面更大。

## 锁定设计

- 入口模块:
  - `sdk/cliproxy/service_auth_maintenance.go`
  - `internal/api/handlers/management/auth_files_runtime_hook.go`
  - `internal/config/config.go`
  - `config.example.yaml`
  - `internal/api/server.go`
  - `internal/api/handlers/management/auth_files.go`
- 关键调用链:
  - `coreauth.Manager.MarkResult -> Service.handleAuthMaintenanceResult -> authMaintenanceCandidateForAuth -> disable candidate -> disableAuthMaintenanceCandidate`
  - `coreauth.Manager.MarkResult -> authRuntimeMaintenanceHook.OnResult -> handleCodexRequestMaintenance / handleUnauthorizedAuthCleanup -> handleManagedAuthDisable`
  - `DELETE /v0/management/auth-files -> DeleteAuthFile / deleteAuthFileByName -> os.Remove + deleteTokenRecord`（保留为唯一删除入口）
- 数据流:
  - `AuthRuntimeConfig.UnauthorizedDeleteThreshold` 与 `AuthMaintenanceConfig` 中的兼容 delete 字段继续解析进入配置结构体；
  - 自动链路只把这些字段当作“触发禁用”的条件，不再产生 delete candidate；
  - 已存在的 `pending delete` 元数据在扫描 / 应用时转为 disable 语义，避免历史状态继续删文件。
- 错误处理:
  - 自动禁用写盘失败时保留原有 warning / persist 行为，不偷偷回退到删除。
  - 直接删除接口仍沿用现有错误处理和回收站/删除记录逻辑。
- 配置变更:
  - 不新增字段、不删除字段；
  - 更新注释与示例，把 `unauthorized-delete-threshold`、`delete-status-codes`、`delete-quota-exceeded`、`codex-max-request-count`、`codex-quota-check-request-interval` 明确成“自动禁用”的兼容语义。
